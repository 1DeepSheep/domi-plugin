# 项目简称、工商主体与别名

创建项目、修正项目名、归档到项目或按名称查重时读取。`name` 是资料库展示及纪要命名使用的品牌／项目简称，`legalName` 是已核实的工商全称，`aliases` 是确实指向同一项目的旧名及中英文别名，三者不能混用。

## 确定项目名

1. 优先使用本轮用户明确确认的品牌／项目简称，其次使用 BP、官网、访谈或已核实历史材料中的实际品牌名。既有资料库记录也可能误用了工商全称，不能仅因它已入库就再次沿用错误名称。
2. 不机械删除城市、“科技”“智能”等词。例如“星澜科技”可以就是品牌名；工商注册名的去后缀结果不等于已经证实的品牌名。不为中文品牌强加英文译名，也不把一个产品、母公司或关联公司未经核实地并入本项目。
3. 公司法定后缀（如有限公司、有限责任公司、股份有限公司、Inc.、Ltd.、LLC）通常应进入 `legalName`，不能默认拼在展示名后。没有独立品牌、且材料确认工商全称确实作为项目名称使用，或用户明确要求保留全称时，才可在本次写入传 `allowLegalName: true`；不可为了绕过校验而声称已经确认。
4. 正式名称未披露时保留现有待核名线索，简短说明缺少可靠名称；不要造一个貌似规范的品牌名。会议日期、技术摘要、受访者履历和评级不属于项目名称。

## 查询与更新

- 使用已确认的简称、中英文别名和工商主体查重；网关项目查询覆盖 `name`、`legalName`、`aliases`，不代表搜索了纪要／研究正文。多条命中时按实际主体证据消歧，不自动合并。
- 旧简称或工商名唯一命中已有项目时复用原 ID 与当前规范名，不创建另一条记录，也不把已修正简称改回旧全称。
- 即使附带项目 ID，通过已知旧别名提交也默认保留当前规范名；只有用户明确要求改回该旧名时才传 `rename: true`，目标仍是工商全称时还需符合上文的 `allowLegalName` 条件。`aliases` 按增量合并保留，传空数组不会清除历史别名。
- 改名先读取完整旧记录，使用原 ID、`expectedRevision` 和 `expectedRecordHash` 提交完整字段。保留原 `legalName` 和别名，旧展示名加入 `aliases`；新发现的工商全称单独写 `legalName`，已确认英文名写 `aliases`。仅修正命名时保留业务 `lastUpdatedAt`，不得清空 Notes、评级、融资等字段。
- 写后回读项目名称、工商名和别名，验证旧名仍能定位同一 ID；项目主页展示新名称。保留既有稳定材料目录与文档索引，不因展示名修正复制一套项目材料。

新项目字段示例（名称均为虚构）：

```json
{
  "name": "星澜科技",
  "legalName": "上海星澜科技有限公司",
  "aliases": ["StarWave"],
  "domain": "AI",
  "subdomains": ["具身智能"],
  "status": "待交流"
}
```

以上示例只展示命名字段，不替代既有项目更新时的完整 payload、分类校验及资料回读。

## 旧飞书主库

仍以实际 schema 的 `公司名称` 字段存品牌／项目简称。有现成工商主体／别名字段时写对应字段；没有时保留在 Notes 的简短主体说明中，不擅自创建表字段。查询时同时检查实际字段与 Notes 中的已确认主体映射，并按原 `record_id` 回读。此分支不调用本地网关，不能声称具有本地别名索引能力。
