# 旧版飞书主库兼容契约

本文件只适用于满足以下全部条件的既有用户：

```text
storageBackend = feishu
localAuthorityMigrationCompleted != true
```

此时设置 `repositoryBackend=legacy_feishu_primary` 与
`legacyFeishuPrimary=true`。在一次任务内锁定该后端：既有项目、人脉、行业
事件、Wiki 文档和 `1.待办事项` 继续按照升级前的飞书主库链路读取和写入，
不得把新数据写进尚未完成导入的本地 SQLite／Markdown 后再让客户端继续读取
飞书。`scripts/domi-repo.cjs` 的项目、人脉、行业、文档和初始化命令在本模式
下均禁止执行。

新安装、明确选择本地主库或已完成安全导入的用户不进入本契约，仍完整执行
`storage-backends.md` 的本地主库规则。对本地主库用户，飞书继续只是按需知识
外挂与发布平台；本兼容契约不得被普通飞书链接、登录状态或写入失败触发。

## 1. 配置与身份守卫

只从 `DOMI_CONFIG_PATH` 读取既有配置，不要求用户重新粘贴，也不得在回答、
产物、日志或仓库中复述任何值。旧主库正常读写需要：

- 项目库 `projectBaseToken + projectTableId`；
- 人脉库 `peopleBaseToken + peopleTableId`；
- 行业动态 `radarBaseToken + radarTableId`；
- `wikiSpaceId`；
- 原有本地材料目录 `localLibraryDir`（兼容 `oneDriveProjectDir`）。

使用当前用户身份和既有完整飞书授权，Base／Wiki／Docs／Drive／IM／Contact
分别采用对应 `lark-*` Skill；若运行环境要求命令行，使用 App 提供的
`lark-cli`，不得查找或下载另一个运行时。目标映射缺失、账号过期、字段不匹配
或身份不唯一时停止当前飞书阶段并给出可恢复提示；不得自动切成本地、创建
同名 Base／Wiki 或猜测另一个用户的资源。

## 2. 项目库与项目文档

项目结构化权威记录继续是既有 Watching List。写入前用项目的中文名、英文
名、品牌／产品名和法律主体查重，并以字段名动态读取真实 schema；项目名称
字段固定按 `公司名称` 语义解析。先运行幂等 `ensure-intake-time-fields.js
ensure`，确认项目表 `入库时间` 为系统 `created_at`，该字段不得进入写入
payload。

项目 intake／update 按以下顺序完成：

1. 用 canonical taxonomy 确定领域、多个子领域和唯一主子领域；
2. 在 Watching List 与 Wiki 中查重，0 条才新建，1 条复用，多条停止确认；
3. 通过 `lark-doc`／`lark-wiki` 在既有 Wiki 空间创建或更新唯一项目文档；
   交流纪要在前、桌面研究作为独立 Part 在后，保留已有图片、附件与用户章节；
4. 源材料、文字稿和二进制附件仍归入原有本地材料目录的唯一项目目录；同文件
   跳过，不同版本并存且名称可辨识；
5. 回读文档核心章节、Wiki 父链和本地材料清单；
6. 最后按唯一业务键 upsert Watching List，并回填已验证的 Wiki URL、Notes、
   分类、进展、评级、历史融资、最新估值、关注投资机构和最后更新时间；
7. 按 `record_id` 重新读取并逐字段核验。记录、Wiki 文档与本地材料三层都通过
   后才返回 `managed`。

新建项目不得只写 Base 或只建 Wiki。更新未知来源的同名文档、覆盖不确定记录
或把研究稿写进另一个项目均禁止。历史融资、最新估值和关注投资机构仍执行
`financing-fields.md` 的业务口径，只是本分支把三个字段写回既有项目 Base。

## 3. 人脉库与交流文档

人脉结构化权威记录继续是既有人脉 Base。写入前读取实时 schema，先按姓名，
再结合所属组织／身份、canonical profile 和已授权标识做唯一匹配；中低置信
匹配不得合并。先运行幂等入库时间迁移，确认 `入库时间` 为系统
`created_at`，并确认存在文本型 `交流文档` 字段。

- 单人且唯一匹配时可按已授权计划 create／update；开放式、批量或冲突计划先
  展示精确变更并等待确认；
- `类型` 只保留一个主类型，其他身份写入所属组织／身份或情报字段；
- 公开人物研究写入当前人物记录的研究信息；真实交流纪要通过既有飞书文档链路
  归档，并把经过回读验证的链接增量写入 `交流文档`；
- 每条写入后按 `record_id` 回读；未找到唯一记录或回读不一致时不得声称入库。

本分支不得同时调用本地 `person upsert`，也不得创建一份只在本地客户端不可见
的第二个人脉记录。

## 4. 行业动态与 Radar

行业事件结构化权威记录继续是既有行业动态 Base。开始批次时一次读取真实字段
schema、项目 Base 的 canonical 分类和发现窗口内既有事件索引；不得逐候选
重复加载整表。重点项目从 Watching List 读取，重点人脉从人脉 Base 读取；
仍执行 Radar 的范围、原文核验、事件级去重、重要性／可信度评分与输出门槛。

- 目标必须是配置中的既有行业动态 Base／Table；不可访问或 schema 不符时只
  返回“搜索完成、归档未完成”，不得另建 Base 或改写项目表；
- 按稳定 `事件ID` 精确去重，0 条创建、1 条仅在实质增量时更新、多条停止；
- 分类选项以项目 Watching List 与 canonical taxonomy 的交集为准；真正的新
  子领域仍走受控分类审核，不由 Radar 猜测创建；
- 写请求结果不确定时先按 `事件ID` 回查，再决定是否重试；成功项批量回读
  标题、时间、URL、评分与分类后才报告归档完成；
- 本分支不得调用本地 `news upsert` 或生成一套客户端看不见的本地事件镜像。

## 5. `1.待办事项`

旧主库模式继续以当前 Wiki 空间中的 `1.待办事项` docx 为客户端与 Skill 的
唯一可写账本，兼容旧标题 `1.Task`／`1. Task`：

1. 优先使用本机已有 `taskDocumentUrl` 无感定位；否则在配置的 Wiki 空间按
   规范标题搜索，旧标题只作兼容；
2. 多个候选时逐个只读解析 caption 为 `domi-task-board-v1` 的账本。唯一非空
   账本胜出；多个非空或无法完整核验时停止，绝不按搜索顺序猜测；
3. 只找到旧标题时可改名为 `1.待办事项` 并回读；找不到时仅在用户明确要求
   生成／更新待办时在既有 Wiki 空间创建；
4. 项目、人脉和行业候选从三个既有 Base 或可信客户端快照读取，先确保项目／
   人脉系统 `入库时间`，不得用最后更新时间伪装新入库；
5. 读取现有 ledger，保留 `open / in_progress / done / ignored`、时间戳与冷却
   状态；只替换 marker 对应的数据块，不覆盖正文其他内容；
6. 单次写入并单次回读完整 ledger。marker、事项数量、ID、状态或关键字段不一致
   时不得更新看板成功状态。

本分支不得初始化或写入 `0.待办事项.md`。只有安全导入全部通过并原子切换为
本地主库后，后续扫描才改用本地账本。

## 6. 安全导入与原子切换

切换到本地主库必须由用户明确发起，并产生可恢复迁移账本：

1. 初始化本地 SQLite／Markdown 后，对既有项目、人脉、行业事件、待办账本和
   Wiki 文档做快照；迁移过程中旧飞书主库仍是唯一写入端；
2. 逐条幂等导入并回读结构化字段、Markdown AST、图片、附件和目录；冲突或
   多候选只暂停对应条目，不覆盖；
3. 最终切换前短暂冻结新的管理写入，补齐快照后的增量，再对数量、业务键、
   内容哈希和文档图片做最终回读；
4. 全部验证成功后，App 在同一配置事务中写入
   `localAuthorityMigrationCompleted=true` 并把 `storageBackend` 切为 `local`；
5. 任一失败都保持 `storageBackend=feishu`，恢复旧主库写入并从迁移账本重试。

迁移永远不删除、移动或覆盖原飞书内容。完成切换后，本地资料库成为唯一权威，
飞书按 `feishu-knowledge-extension.md` 退回按需知识外挂／发布平台。
