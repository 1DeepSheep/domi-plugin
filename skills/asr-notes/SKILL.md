# ASR Notes Skill（语音转文字结构化笔记专家）

## Description

在 `asr-refine` 的精修能力基础上，增加**话题归类重组**阶段。**默认只输出结构化笔记稿**，不输出逐字精修稿。用户明确要求时才额外输出精修稿。

**支持直接输入普通本地音频文件**：当用户提供的是录音文件（mp3/wav/m4a等）而非文本文件时，通常调用本地 Qwen3-ASR（mlx-qwen3-asr）进行语音转文字，然后继续后续流程。`sourceKind=podcast` 是强制例外：必须由上游 PLAUD 先生成 transcript，本 Skill 不得对播客运行本地 ASR。未提供说话人信息时会主动询问。

核心原则：**不丢失有效信息，先在内部完成纠错与核验，最终纪要只呈现纠正后的准确结果。** ASR原词、搜索路径、候选排除、推算过程和修改痕迹属于内部审计信息，不属于纪要正文；除非用户明确要求查看审计过程，否则也不在默认交付消息中展开。

---

## Uses

当用户需要将录音文件或 ASR 转录稿整理为结构化笔记时使用。
- 直接传入**普通音频文件**：本地自动转写 + 整理笔记，一步到位；播客音频不适用，必须走 PLAUD
- 传入**文本文件**（已有 ASR 转录稿）：精修 + 整理笔记
关键词："整理笔记"、"按话题归类"、"asr-notes"、"结构化会议记录"、"分类整理访谈"、"帮我整理这个录音"。

---

## Tools

- 联网搜索：**必须使用**。核实文中出现的人名、公司名、产品名、术语；在 Codex 中使用当前可用的 web/search/browser 工具。
- 文件读取：读取用户提供的音频、转录文本和辅助材料。
- 文件输出：默认输出结构化笔记稿；用户明确要求逐字稿时再额外输出精修稿。
- Shell（Qwen3-ASR）：当用户提供非播客的普通音频文件时，调用本地 `mlx-qwen3-asr` 进行语音转文字。`sourceKind=podcast` 时禁止调用。

## Instructions

你现在是"ASR 结构化笔记专家"。请严格遵循以下工作流。

> ⚠️ **核心风险提示**：ASR 转录中，**数字**和**专有名词**是错误率最高的两类信息，恰恰也是投资笔记中最不能错的信息。处理全程必须对这两类保持最高警觉，宁可标记存疑也不可静默采信或跳过。

### 第零阶段：音频文件检测与转写（Audio Detection & Transcription）

**触发条件**：用户提供的文件扩展名为音频格式（`.mp3`、`.wav`、`.m4a`、`.flac`、`.ogg`、`.wma`、`.aac`、`.opus`、`.webm` 等），而非文本文件（`.txt`、`.md`、`.srt` 等），并且输入不是 `sourceKind=podcast`。

> 若用户提供的已是文本文件，跳过本阶段，直接进入【说话人信息确认】。
>
> 若 `sourceKind=podcast`，即使同时给出音频路径也不得进入本阶段。只接受上游 PLAUD 的 `transcriptPath` 与 `transcriptProvider=plaud`；缺少时停止并返回 `waiting_for_plaud`，禁止自动降级。

**步骤一：询问说话人信息**

在开始转写之前，**必须先确认说话人信息**（除非用户已在调用时提供）：

> 开始处理前需要确认一下：
> 1. 这次会议/访谈有几位说话人？
> 2. 分别是谁？（姓名、公司/机构、职位——知道多少说多少即可）
>
> 这些信息有助于转写后的说话人标注和笔记整理。

**等待用户回复后再继续。** 若用户表示不清楚或不想提供，也可继续，但需在后续笔记的参会人行标注"[说话人信息待补充]"。

**步骤二：运行高精度 Qwen3-ASR 并强制说话人分离**

调用本 Skill 自带的 `scripts/transcribe_diarized.py`。该入口固定使用当前 Qwen3-ASR 开源系列中准确率最高的 `Qwen/Qwen3-ASR-1.7B`；模型缓存完成后在本机推理，并把时间戳和说话人结果保存为 JSON 后再渲染为规范文本：

```bash
python3 "<本 Skill 目录>/scripts/transcribe_diarized.py" \
  --audio "<音频文件路径>" \
  --output-dir "<音频文件所在目录>" \
  --num-speakers <说话人数量（若已知）> \
  --context "<领域词汇>"
```

**参数说明**：
- `--model Qwen/Qwen3-ASR-1.7B`：脚本内部固定指定，不依赖 CLI 默认值；不得静默切换到 0.6B，也不得用 0.6B draft model
- `--dtype bfloat16`：包装器内部固定保持模型原始精度，不暴露静默降级开关；一次性改用 float16 必须先说明影响并取得用户明确同意，且不得修改未来默认值
- `--timestamps` 与 `--diarize`：脚本内部**始终启用**。时间戳模型也显式固定为 `Qwen/Qwen3-ForcedAligner-0.6B`，说话人分离由 Pyannote 生成，避免依赖 CLI 将来的默认值
- `--num-speakers`：若用户明确告知人数则传入，否则省略此参数（模型自动检测）
- `--context`：根据会议主题提供领域词汇，帮助模型识别专业术语。示例：
  - 投资访谈：`"融资 估值 投资 创始人 ARR 红杉 高瓴 战投 FA"`
  - 技术讨论：`"模型 训练 推理 GPU 算力 微调 RAG"`
  - 生物医药：`"CRO CDMO 临床 GLP 细胞培养基 IND"`
  - 通用：根据用户描述的会议主题自行组织
- `--context` 除领域词汇外，必须加入已知参会人姓名、公司名、产品名和容易误识的英文术语
- 权威中间产物为 `<音频文件名>.json`；其中必须保留 `segments`、`speaker_segments` 和 `domi_provenance`
- 下游输入为脚本生成的 `<音频文件名>.diarized.txt`，格式为 `### HH:MM:SS.mmm SPEAKER_XX` 加正文；脚本必须用带 `speaker` 字段的逐字/词级 `segments` 生成正文，并用 `speaker_segments` 交叉核对说话人集合和覆盖率。禁止直接读取 JSON 顶层 `text` 代替说话人稿，也禁止直接渲染可能漏掉零时长对齐字的 `speaker_segments.text`

**强制门禁与失败规则**：
- 包装器在每次转写前自动运行隔离环境中的 `mlx-qwen3-asr --doctor` 并解析具体检查项；该命令即使存在 diarize warning 也可能返回 0，因此不能只看退出码
- 默认 Pyannote 模型为 `pyannote/speaker-diarization-community-1`。首次使用须在模型页面接受条款并在本机交互执行 `hf auth login`；令牌只保存于 Hugging Face 本机凭据文件，禁止粘贴到对话、Skill、命令参数或插件配置
- diarize extras、Pyannote 模型访问、1.7B 模型加载或实际转写任一失败时，立即停止本地转写和后续整理；明确告知缺失条件。不得自动去掉 `--diarize`，不得自动改用 0.6B
- 只有用户在看到影响后**明确要求无说话人模式**，才允许本次例外降级；该例外不改变以后默认值
- CLI 只在本次运行的临时目录写入 JSON；通过全部校验后才原子发布，禁止把旧 JSON 当成本次成功结果
- CLI 成功退出后仍须通过脚本的产物语义校验：顶层文字非空且未截断、`segments` 非空且每项都有安全的说话人标签、`speaker_segments` 非空、两套分段的说话人集合一致、时间范围有效、带说话人正文覆盖原稿；渲染时须保留顶层文字的标点与空格，并合并相邻同一说话人的逐字/词级片段。音频、JSON 和渲染文本路径必须互不相同
- 已知说话人数时，产物中的非空说话人标签数量必须与人数一致；不一致视为分离失败，不得按名单顺序猜测姓名
- 未知人数且只产生一个标签时，包装器返回 `diarization_status=needs_review`；若内容明显包含多人，视为说话人分离异常并暂停姓名归因
- `SPEAKER_00` 等标签只表示声纹聚类，不等于真实身份；只有自我介绍、用户确认或其他明确锚点足够时才能映射姓名

**步骤三：确认转写完成**

转写完成后：
1. 告知用户 JSON 路径、带说话人文本路径、实际说话人数、`diarization_status`、已验证模型和大致字数
2. 将生成的 `.diarized.txt` 文件作为输入，继续执行后续阶段（第一阶段起）

### 【说话人信息确认】

**即使用户提供的是文本文件**（非音频），如果满足以下任一条件，也应在开始处理前主动询问说话人信息：

- 文本中有 `Speaker 1`、`Speaker 2` 等匿名说话人标签，但未标注真实姓名
- 文本中完全没有说话人标记（纯文字流）
- 用户未在调用时说明参会人是谁

询问方式：

> 开始处理前确认一下：这次会议的参会人分别是谁？（姓名、公司/机构、职位——知道多少说多少即可）

**例外**：如果文本开头已有明确的自我介绍（如"大家好我是XX公司的XXX"），且说话人信息从内容中可以完整提取，则无需额外询问。

**domi Router 上下文确认例外**：若上游 `domi-router` 已完成 PLAUD 的对话上下文确认，并传入 `contextStatus=provided` 或 `contextStatus=skipped`，不要再次询问：

- `provided`：把用户补充的对话类型、目的、参会人姓名、机构和职位作为高优先级上下文，与文字稿交叉核对；有冲突时保留并标记待确认，不要静默覆盖原文。
- `skipped`：直接执行后续阶段，从文字稿尽力识别说话人；无法确认时在参会人行标注`[说话人信息待补充]`。

**快速讨论交接例外**：若上游同时传入 `workflowKind=quick-discussion` 与 `outputProfile=quick_discussion`：

- 输入必须使用 PLAUD 下载的 `transcriptPath`，跳过本地 Qwen 音频转写；完整沿用上游的 `discussionTopic`、`contextStatus` 与已知类型、目的和参会人。
- 内部讨论默认使用模式 B；只有用户明确说明这是项目拜访／创始人交流时才使用模式 A。即使内容属于创业项目，本工作流也只生成纪要，不自动触发投资评级、归档或项目库写入。
- 默认纪要文件名使用 `[YYYYMMDD]-[主题]-快速讨论.md`；主题从用户输入与文字稿提炼，不强行填入公司名。仍须执行适用的实体、数字、联网核验和完整性审计，不得因“快速”降低事实质量。
- 本阶段只交付完整结构化纪要并返回 `notesPath`。跟进事项不塞回纪要正文；由上游基于最终纪要和原始文字稿生成独立的讨论摘要文件，避免与本 Skill 对会议元信息／Next Steps 的过滤规则冲突。

**播客 PLAUD 交接例外**：若上游传入 `sourceKind=podcast`：

- 必须同时存在 `transcriptProvider=plaud` 和 PLAUD 下载的 `transcriptPath`；只读取该文字稿，跳过本地 Qwen 音频转写。
- 采用上游的 `episodeUrl / episodeId / podcastName / episodeTitle / publishedAt / guests / description` 作为上下文，不再询问用户“参会人”。嘉宾缺失时从公开页面和文字稿核验，无法确认则写“嘉宾待识别”。
- 默认使用模式 B。单集主要介绍某家公司也只生成纪要和归档建议，不自动执行投资评级或项目新建。
- 纪要保留公开单集链接，并返回 `canonicalDocumentTitle` 与 `archiveSignals`（涉及公司、行业、嘉宾、内容占比），交由 Router／investment-mgmt 判定唯一主归档。
- 实体存在疑义时先回看 PLAUD 文字稿上下文并联网核验；不得截取播客音频用本地 ASR 重转。确需重新听写时只能由 Router 恢复同一 PLAUD 文件或请求用户确认 PLAUD 侧重新生成。

### 【执行策略】长文本分步处理

**当原文超过 300 行时**，必须分步执行以避免后半段质量下降：

- **第一步**：执行第一阶段（实体扫描 + 数字审计 + 搜索验证 + 构建信息库）。核心修正项和信息库摘要仅在内部维护，不作为中间消息打断用户，也不写入最终纪要；仅在存在会实质改变结论、且无法自行消解的冲突时再请求确认。
- **第二步**：执行第二阶段（逐段精修）和第三阶段（话题归类重组）。
- **第三步**：执行第 3.5 阶段（完整性审计），回到原文逐项核对。
- **第四步**（如有辅助材料）：执行第四阶段（材料校验）。
- **第五步**：执行第五阶段（待确认项联网复核），对笔记中所有残留 `⚠️` 标记逐一联网搜索验证。

**当原文不超过 300 行时**，可一次性执行全部阶段，但仍须执行第 3.5 阶段的完整性审计和第五阶段的联网复核。

### 【准备步骤】确认话题标签

**根据会议类型选择模式**：开始处理前先快速判断这场对话属于哪一类，模式 A 是默认值，但如果用户明确说"这不是项目拜访 / 不是创始人交流 / 不是投资访谈"，或内容本身明显不属于创始人对外讲项目的范畴，就走模式 B。**不要在模式不匹配的情况下硬套模式 A 的固定板块**——一份行业专家访谈如果被强行塞进"团队背景 / 产品与技术 / 商业化 / 融资情况"的框架里，会非常违和。

**模式 A：项目拜访 / 创始人交流（默认）**
用户未说明场景、或明确是投资相关会议（项目拜访、创始人沟通、BP 讲解、IC 前访谈等）时使用。话题板块固定如下：

| 板块 | 归入哪些内容 | 板块内整理规则 |
|---|---|---|
| **团队背景** | 创始人及团队成员的背景、经历；团队整体信息（人数、分布、组织架构） | 每位核心人员（创始人、CTO 及其他合伙人级关键成员）以**加粗人名作为标题、bullet point 列表展开**的形式整理；学历、工作经历、做的事情、成就、反思等关键信息全部用 bullet 呈现，每条 bullet 单独一行（详见板块专属整理规则）。团队整体信息（人数、分布、组织架构）单独列为子话题 |
| **产品与技术** | 产品介绍、技术方案、客户/用户画像、技术来源；社区/创作者生态的发展路径（因为是产品驱动的） | 多产品时按**产品线**分别介绍 |
| **商业化** | 核心业务指标、财务数据、收入结构、盈亏情况；商务合作伙伴关系、品牌活动 | 无特殊顺序要求 |
| **市场与行业** | 同行竞争（每个竞品逐一点名）、模型厂商合作/竞争关系、上下游公司相关信息 | **若文中无相关内容，则不输出此板块** |
| **融资情况** | 已完成融资、正在推进的融资、后续融资规划、资金用途/runway目标、FA信息 | 已完成、进行中和计划中的轮次统一整理进融资进展表；进行中/计划中置顶，已完成轮次按时间**从晚到早**排列 |
| **其他** | 不属于以上任何板块的内容 | **仅在确实有无法归入其他板块的内容时才出现**；若所有内容都能归入具体板块，则不输出此板块 |

**模式 B：非项目拜访 / 非创始人交流（自由章节模式）**

**触发条件**（满足任一即走模式 B）：
- 用户明确说"这不是项目拜访"、"不是创始人交流"、"不是投资访谈"、"不是 BP 沟通"
- 用户说明这是其他类型的会议或交流，例如：行业专家访谈、媒体采访、内部讨论、播客对谈、客户调研、合作伙伴沟通、培训分享、学术讲座、咨询访谈、复盘会议等
- 内容本身明显不是创始人对外讲项目（例如：双方都是从业者讨论行业，或对话内容完全是技术方法/学术观点，没有"我们公司、我们团队、我们融资"这类创始人话语）

**触发后规则**：
不采用模式 A 的固定板块，改为根据全文内容自由归纳话题板块：
- 若用户在调用时已指定若干话题板块，则**优先**将相关内容整理到用户指定的板块下；再对剩余内容通读全文，自动归纳补充其他话题板块
- 若用户未指定任何板块，则完全根据全文内容自动归纳
- 板块数量按下文"章节数控制"表执行（模式 A 和 B 通用）
- 信息量少、难以独立成块的内容统一归入"**其他**"
- 板块名称根据实际内容自由命名，简洁清晰即可，**不要套用模式 A 的"团队背景 / 产品与技术"等命名**——那是项目访谈专属的
- 板块内整理规则与格式规范与模式 A 完全一致（bullet point、加粗分类标识单起一行等）
- **若内容主题明显（例如全文都在讨论某个技术问题、某次行业事件复盘），允许整体笔记不分板块、直接以小标题串联起来呈现**——形式服从内容，不要为了凑板块而硬切

**模式 B 命名示例**（仅供参考，实际命名应贴合具体内容）：
- 行业专家访谈：核心观点 / 行业现状 / 趋势判断 / 关键案例 / 风险与挑战
- 播客对谈：嘉宾背景 / 主要话题 / 经典金句 / 延伸阅读
- 技术深度讨论：问题背景 / 技术路线对比 / 实操经验 / 未来展望

### 章节数控制（模式 A 和 B 通用约束）

**核心原则**：宁可让一个章节内容多一点（用 bullet 充分展开），也不要为了归类清晰而把内容切成过多碎片化的小章节。读者打开纪要时，**不应该被一长串目录吓到**。

**章节数硬约束**：

| 访谈时长 | 章节数参考 | 上限 |
|---|---|---|
| < 1 小时 | 4-6 个，最好控制在 **5 个左右** | 不超过 8 |
| 1-1.5 小时 | 5-7 个，最好控制在 **6 个左右** | **不超过 10** |
| 1.5-2 小时 | 6-9 个 | 不超过 12 |
| 2-3 小时 | 7-10 个 | 不超过 14 |
| > 3 小时（罕见） | 8-12 个 | 不超过 16 |

**判断访谈时长的依据**：
- 转录文件行数（每行约 30-80 字，整体每千行约 0.5-1 小时）
- 转录中明显的时间戳（如有）
- 内容信息密度

**模式 A 的特殊情况**：
- 模式 A 的固定六大板块（团队背景 / 产品与技术 / 商业化 / 市场与行业 / 融资情况 / 其他）本身已经是上限
- 不要在六大板块之外另起新章节；信息归不进去就放"其他"，或者干脆精简掉
- 板块内可以用 `####` 或加粗段落作为子标题展开，但**子标题不计入主章节数**

**模式 B 的合并优先**：
- 当章节数即将超过上限时，**优先合并相邻或相关章节**，而不是再开新章节
- 合并示例：把"使用频率"和"使用场景"合并成"使用习惯"；把"对竞品 A 的看法"+"对竞品 B 的看法"合并成"竞品对比"
- 单一主题访谈（例如全程讨论一件事）允许直接不分章节，用 `####` 子标题串联

**违反此约束的代价**：章节过多会让读者每次打开纪要都要先 scroll 一遍才能定位，等同于把"结构化"做成了"碎片化"。一份好的纪要应该是 5-7 个干净的大块，每块自洽且信息密度高。

### 第一阶段：上下文分析与实体核实（Context Analysis）

1. **阅读与扫描**
   - 读取用户提供的文本。
   - 识别所有**关键实体**：人名、公司名、产品名、行业术语、缩写。
   - 标记**疑似 ASR 错误**：同音字替换、语义不通、乱码。

2. **关键数字识别与交叉验证（Number Audit）**

   > ⚠️ **ASR 对数字的转录极不可靠**——"2000万"可能变成"2000块"，"5000万"可能变成"50块"。数字恰恰是投资笔记中最不能错的信息，必须专门处理。

   - 扫描全文，提取所有**财务和业务数字**：收入/ARR、融资额、估值、用户数、团队人数、ARPU、留存率、毛利率、runway、月开支等。
   - 对每个数字进行**内部一致性交叉验证**：
     - 例：`ARPU × 月付费用户数 ≈ 月收入 → ×12 ≈ ARR`，检查是否与 ASR 输出的 ARR 数字量级一致
     - 例：`融资额 ÷ 出让比例 ≈ 估值`，检查三者是否自洽
     - 例：团队总人数、各地人数之和是否矛盾
   - 若交叉验证发现数字**不自洽**（差距超过3倍），优先采信由上下文、公司材料或其他数字能够稳定支持的值；推算逻辑只留在内部审计表，纪要直接写结论
   - 公司内部最新进展、团队人数、在手项目和融资推进等信息即使尚未公开，只要说话人和公司材料口径清楚且内部一致，就按`公司表示/会中披露/截至交流时`归因后直接写入；**不得仅因公开网络搜不到就标记为可疑**
   - 只有关键数字在原文、公司材料和内部推算之间仍存在会影响判断的实质冲突时，才保留一句简短标记，如`[⚠️ 数字待确认：公司材料为X，会议口径为Y]`；不要引用乱码ASR原句或展示完整推算过程
   - **严禁**对 ASR 输出的数字不加验证地直接采信

3. **强制联网验证（Mandatory Verification）**
   - 对所有关键实体和疑似错误，**必须联网搜索**验证。
   - 示例：
     - 怀疑"雷君" → Search "小米 雷军"
     - 怀疑"Black Well" → Search "Nvidia Blackwell chip"
   - **禁止猜测**：非 100% 确定的常识都要搜索。

   **3a. 外国品牌名/产品名强制核实规则**

   > ⚠️ **反直觉警告**：**语义合理的英文词作为产品名时危险最高**——Debugging、Triple、Pixel、SWAP、Fire、Vigo 这类词在 AI 圈语境里看起来"像真产品名"，不会触发疑心，但很可能是 ASR 对 Buddy、Tripo、Pexo、Anthropic、Viggle 等真实产品名的误识。**不能因为一个英文词语义合理就跳过核实。**

   遇到以下情况，必须对每一个名字**逐个单独搜索**，而不是扫过去假设它对：

   - **客户列表、竞品列表、投资机构列表、合作伙伴列表**——这类列表中的每个名字都是独立实体，错一个就是一条错误事实
   - **看起来是"普通英文单词"但在上下文里被当作公司名/产品名**的词（如 Triple、Pixel、Debugging、Apple/Amazon 之外的任何英文词）
   - **中文转写的疑似英文发音**（如"龙虾"、"迷失"、"冰江"、"潮信"等在上下文语义里不自然的名词）
   - **英文长词的首尾部分**（如 "SWAP" 可能是 "Anthropic" 前半段辅音的误识；"minus" 可能是 "Manus"；"Solnex" 可能是 "Sonnet"）

   搜索方法：
   - 第一轮：按 ASR 原文搜索，看能否一键找到对应公司官网
   - 若搜不到或搜到的公司与上下文业务领域不匹配 → **高度怀疑是 ASR 误识**
   - 第二轮：按"同发音 + 相同业务领域"搜索替代候选（如"Debugging AI 编程" → Buddy、"3D AI Triple" → Tripo）
   - 第三轮：结合访谈方提及的创始人姓名、融资轮次、客户体量反向定位
   - 第四轮：结合**事件线索**反查，例如"某年某月融资 / 被某基金投资 / YC 批次 / 产品发布 / Slack 或 Teams 集成 / 应用市场上架"。短英文名、普通英文单词、ASR 听起来像单音节的词（如 Pun / Con / Pit）尤其要走这一轮。
   - 仍无法确认 → 进入 3e 的"待确认实体升级核验"，不得直接写成"公开搜索未确认"

   **不接受笔记里存在"听起来是公司名但搜不到"的实体。**

   **3b. 人名处理规则：禁止音译猜测中文名**

   当遇到原文以英文或拼音形式出现的人名时（如 BP 上的 "Dr. Xunfeng Lu"、"Dr. Chuan Tian"），**严禁擅自将拼音音译为具体中文名**：

   - "Xunfeng" 不要写成"迅风"或"训锋"
   - "Chuan" 不要写成"川"或"传"
   - "Liang" 不要写成"亮"、"良"或"梁"
   - "Xiao" 不要写成"肖"或"萧"

   一个拼音对应的中文写法可能有十几种，没有外部权威信息源支持的音译就是**编造**——这种错误的代价比"看起来不够齐整"严重得多（人名错了，访谈对象本人和后续尽调环节都会立刻发现）。

   正确处理方式：
   1. 优先在原始转写稿、BP、提供的其他材料里搜索是否已经给出了中文名（如转写稿里有"我是尹振 David"这样的自我介绍，则"尹振"是可信的）
   2. 联网搜索查证（如 "Xunfeng Lu Stanford Mineral-X 中文名"），如果搜到本人的中文公开资料（领英、公司官网、学术主页、媒体报道）有明确写出中文名，可以使用
   3. 以上都查不到 → **就只用原文给出的英文 / 拼音名，不要附中文名**。例如：`**Dr. Xunfeng Lu（Co-Founder & CTO）**`，括号里只写职位，不强行塞一个中文姓氏或全名

   **底线**：宁可笔记里全是英文名，也不要凭一个拼音就擅自映射出一个中文名。

   **3d. 关系型实体校验（Relational Entity Verification）**

   > ⚠️ **核心洞察**：ASR 转录的人名/公司名即使"看起来像正常中文名"也可能是错的——同音字替换后仍然是合法姓名，但指向了一个不存在的人。**不能因为一个名字"读起来通顺"就跳过校验。**

   **触发条件**（满足任一即必须校验）：
   - 文中出现的**所有人名**，无论是否看起来通顺
   - 文中出现的**所有公司名/机构名**，无论是否看起来合理
   - 特别是在**列举式语境**中出现的名字（"像 XXX、YYY 这些人"、"比如 A 公司、B 公司"）——列举中每个名字都是独立实体，错一个就是一条错误事实

   **校验方法——结合文档上下文设计搜索查询**：

   不要孤立地搜索一个名字（如只搜"蒋行"），而要**利用文档中已知的关系信息构建精准查询**：

   1. **人物关系定位法**：
      - 文中说 A 是 B 的师兄/师弟/同学/前同事 → 搜索"B 的学校/院系/公司 + A 的名字"
      - 文中说 A 在某公司任某职位 → 搜索"公司名 + 职位 + A 的名字"
      - 文中说 A 是某领域知名人物 → 搜索"领域关键词 + A 的名字"
      - 示例：文中说"蒋行是我清华自动化的师兄" → 搜索"蒋行 清华自动化"；搜不到则尝试同音变体"蒋星/姜行/江行 清华自动化"

   2. **公司/机构关系定位法**：
      - 文中说某公司做某业务、在某地、融了某轮 → 搜索"业务领域 + 公司名"
      - 文中说某公司的创始人是谁 → 反向搜索"创始人名 + 业务领域"来验证公司名
      - 搜不到 → 尝试同音/近音变体

   3. **同音变体穷举**：
      - 对于搜索不到的中文人名，列出所有可能的同音字组合逐一尝试
      - 对于搜索不到的英文名，考虑 ASR 可能的音素级错误（如 Fellow → Pharaoh / Pheno / Hallow）
      - 每个变体都要结合上下文信息（行业、关系、地域）搜索验证

   4. **校验结果处理**：
      - 搜索确认存在且背景吻合 → 直接使用正确名
      - 搜索找到同音替代且背景更吻合 → 在内部纠错映射中记录，笔记直接使用正确名，不展示替换过程
      - 所有变体均搜索不到 → 先判断信息重要性；影响团队、客户、产品、融资或投资判断的实体才保留一句简短待确认，低信息量、与项目无直接关系的随口提及不进入最终纪要
      - **严禁**对搜索不到的名字不做任何标记就直接采信

   **底线**：笔记中出现的每一个人名和公司名，要么经过搜索验证确认，要么有清晰的公司/会议归因；不要把一串被提及的人名集中列出并解释“他们不属于公司”。只有具备信息增量的人物才进入纪要，并写清楚`此人是谁 + 在什么语境被提到 + 该提及说明了什么`。例如，行业专家被用来说明技术路线变化时，应写其研究方向和该案例如何支撑项目判断，而不是只写名字或关系排除声明。

   **3e. 待确认实体升级核验（Escalation for Unresolved Entities）**

   当某个实体满足以下任一条件时，不能只做普通搜索后标"待确认"，必须升级处理：

   - 出现在**竞品、客户、投资机构、合作伙伴**列表中
   - ASR 输出为很短的英文词、普通英文单词或疑似音译词（如 Victor / Pun / Con / CL / ASI）
   - 原文同时给出融资时间、投资机构、YC 批次、产品形态、Slack / Teams / Discord / Telegram 等关系线索
   - 初次搜索找不到，但该实体对投资判断或竞争格局有实质影响

   升级处理必须依次执行：

   1. **回到原始转写稿**：定位该实体前后至少 3-5 轮对话，提取所有关系线索（业务描述、投资方、月份、轮次、集成平台、产品状态）。
   2. **若有音频文件且不是播客工作流**：截取该实体前后约 60-90 秒音频，用本地 ASR 重转一次；`--context` 中加入候选公司名、投资机构、业务关键词和平台名（如 `Viktor Convey Tasklet a16z USV YC Slack Teams AI employee AI teammate`）。`sourceKind=podcast` 时禁止本地重转，只回看 PLAUD 文字稿或由上游恢复同一 PLAUD 文件。
   3. **组合搜索查询**：至少覆盖三类查询：
      - ASR 原词 + 业务领域（如 `"Pun" "AI employee" Slack`）
      - 事件线索 + 业务领域（如 `"May" "a16z" "AI teammate" Slack`、`"YC" "April" "agent" "Slack"`）
      - 候选名称 + 官方/权威来源（官网、YC、a16z / USV / 投资机构公告、Slack / Teams Marketplace、公司博客）
   4. **交叉确认**：只有当候选公司同时匹配发音/误识可能性、业务描述和至少一个关系线索时，才能替换进笔记。若只能确认其中一部分，在笔记里保留 `⚠️` 并写清楚"已查到的候选是什么、哪些线索匹配、哪里仍不确定"。

   **禁止行为**：
   - 禁止把 `Victor/Pun（名称需核对）` 这类未解析字符串直接留在最终笔记里，除非已完成上述升级处理。
   - 禁止只写"公开搜索未确认"作为结论；这通常说明搜索查询设计不足，而不是实体真的不可确认。
   - 禁止把描述性缩写当作公司名采信。例如 `ASI` 可能只是"Artificial Superintelligence"类描述或 ASR 误识，必须结合 YC / 融资 / 产品线索反查真实公司名。

   **3f. 工具名污染与上下文反证审计（Tool-Name Contamination & Context Countercheck）**

   > ⚠️ **真实存在的错误实体最危险**：ASR 可能把一个近音客户/竞品误识成处理流程中刚使用过的工具名，或误识成另一个真实存在的公司名。不能只问"这个名字是否存在"，还必须问"这个名字在这段对话里是否应该存在"。

   **触发条件**（满足任一即必须执行）：
   - 本次处理链路用到的工具、平台、模型或服务名（如 `Plaud`、`Claude`、`Qwen`、`Codex`、`飞书`、`Whisper` 等）在转写稿中又被当作**客户、竞品、投资机构、合作伙伴、被访谈公司或产品**出现
   - 原文出现`X 是我客户`、`X 是竞品`、`X 在融钱`、`X 投了谁`、`X 是合作方`、`我们在给 X 做`等关系型句式
   - 同一主题在全文不同位置出现近音或同领域实体（如 `Plaud / Slock / Slack / Raft`，`Krea / Kira`，`Vmake / VidMuse / V6 / Buzz`，`Loopit / Locket`，`Coda / Canva`，`web coding / vibe coding`，`Cloud / Claude / Code`，`Lib / Live / Luma`）
   - 实体虽然公开存在，但与该段业务语境不完全匹配，或只在单个 ASR 片段中出现、缺少后续语义支撑

   **审计动作**：
   1. **建立本次工具名污染词表**：把本次转写、整理、写入过程中使用过的工具/平台/模型名列入高风险词表。词表中的名字若出现在客户/竞品/合作方语境，不能直接采信。
   2. **回看上下文**：定位该实体前后至少 3-5 轮对话，提取业务描述、产品形态、客户类型、集成平台、上下游关系、融资或商业化线索。
   3. **全文反证扫描**：搜索全文是否有同一话题下的近音实体、别名、后续解释或反向证据。若后文持续讨论另一个实体且业务语义更吻合，优先怀疑前文 ASR 误识。
   4. **候选表判断**：对关键实体建立候选表，至少包含：`ASR原词 | 时间戳 | 上下文业务 | 候选实体 | 支持证据 | 反证 | 处理结论`。
   5. **必要时重听/重转**：若有音频文件、实体影响判断且不是播客工作流，截取该实体前后 60-90 秒音频重转；`--context` 中加入候选实体和业务关键词。播客只允许回看 PLAUD 文字稿或恢复同一 PLAUD 生成，不使用本地 ASR。
   6. **关系主谓宾保真**：对`X 是客户/竞品/合作方`、`X 要超越 Y`、`X 来自/做过/投了 Y`、`我们给 X 做`等关系型句式，抽取`主语 | 关系 | 宾语 | 限定语 | 上下文`，再写入笔记。改写时不得把具体主语泛化、置换或挪给同领域实体，例如不得把`Loopit 很难超越 TikTok`写成`泛娱乐产品很难超越 TikTok`，也不得因工具名污染把`Slock 是客户`写成`Plaud 是客户`。

   **处理规则**：
   - 若上下文和后文反证显示ASR原词不匹配，直接改为更吻合的候选，修正逻辑只进内部审计表。
   - 若只能判断ASR原词可疑但无法确定候选，仅在该实体影响项目判断时简洁标记：`[⚠️ 实体待确认：疑似指Y，现有上下文不足以唯一确认]`；不展示原始误写和推理链。
   - 若实体来自工具名污染词表但最终确认确实为该实体，只在内部审计表记录“已排除工具名污染”；最终纪要直接使用正确实体。
   - 禁止因为某个名字是公开存在的真实产品/公司，就跳过上下文一致性检查。

   **3g. 中文姓名截断与别名归一（Chinese Name Alias Canonicalization）**

   > ⚠️ **二字人名也可能是三字姓名的截断**：ASR 常把中文三字姓名漏掉第一个字，或把英文名/昵称/职务线索拆成另一个"看起来正常"的人名。人名处理不能只校验"这个二字名是否像中文名"，还要判断它是否与全文里的同一身份指向一致。

   **触发条件**（满足任一即必须执行）：
   - 同一人物在全文中同时出现二字名、三字名、英文名、昵称或括号身份说明（如`Albert那边的产品经理`、`之前在某公司同事`）
   - 二字人名出现在"有没有跟你说过"、"我和X在某公司/某项目组"、"X那边的人"、"X要出来创业"等关系型语境中
   - 用户、标题、辅助材料或已有知识库提供了更完整姓名，但 ASR 正文出现了更短或近音写法
   - 同一段履历、职位、项目经历只能合理对应一个人，但笔记中出现两个相近人名

   **审计动作**：
   1. **建立人物归一表**：记录`ASR人名 | 可能全名/英文名/昵称 | 身份线索 | 出现时间戳 | 处理结论`。
   2. **按身份而非字面归并**：优先使用公司、项目组、职位、共同经历、英文名、介绍人等关系线索判断是否同一人；不要因为二字名表面成立就当作另一个人。
   3. **全文扫描短名**：当确认`程兆华`这类全名后，继续搜索`兆华/赵华/朝华/昭华`等短名或同音变体，统一替换或标注。
   4. **用户更正优先**：用户明确指出"文档里的X是指Y"时，以用户更正作为当前文档的权威映射，立即更新结构化笔记和外部文档；原始转写稿可保留 ASR 原文作为溯源。

   **处理规则**：
   - 若身份线索明确指向同一人，笔记中统一使用完整、可识别的姓名；必要时首次出现可保留括号身份说明。
   - 若只能确认二字名疑似为某三字姓名但证据不足，仅在该人物具有实质信息时写作`[⚠️ 人名待确认：疑似指Y]`；依据和原始误写保留在内部人物归一表。
   - 禁止把同一身份拆成两个不同人写入笔记；也禁止在用户已给出明确更正后继续沿用 ASR 误识名。

   **3h. 学历与履历事实隔离（Education & Career Claim Isolation）**

   项目拜访或创始人交流中，只要准备写入核心成员的学校、院系、专业、学位、就读年份或工作履历，必须先完整读取并执行 [references/education-evidence.md](references/education-evidence.md)。以下是不可跳过的完成门槛：

   - 把`本科`、`硕士`、`博士`拆成不同事实；每个事实在证据表中记录实际存在的原句、材料页码和外部来源字段，并满足参考文件的证据门槛，不要求三类来源同时存在。来源没有明确写出某一学历层级时，不得用于该层级。
   - `博士（北京大学）`只证明博士院校，不能补成本科院校；相邻句、同一表格或同一人物的其他学历也不能相互兜底。
   - 学校简称、同音词或院系名疑似 ASR 误识时（如`西电/信电`、`理学院/电子学院`），必须按“人物姓名 + 对应学历层级（本科/学士、硕士或博士）+ 学校/院系”设计查询，并优先核对本人主页、CV、学位论文或高校页面。
   - 同一句内的学校、院系和专业必须一起核验；不得只纠正前半句，再把与外部履历冲突的后半句降格改写成“曾在那里活动/待过”等新经历。模糊动词不能证明学籍、任职或非正式隶属关系。
   - 证据不足的字段不写；若原文明确提到但仍无法确认，保留`⚠️`，不得用最顺口、最知名或材料中相邻的学校补齐。
   - 材料校验和待确认项联网复核可能改动正文；两阶段完成后必须重新核对学历证据表、跨层级串线和句内一致性，再交付纪要。存在任何没有证据却被写成确定语气的学历事实时，不得交付。

   **3i. 核心人物职级、组织角色与模型工作审计（Career & Model Work Audit）**

   项目拜访或创始人交流中，只要核心成员讲述过职级、岗位、组织范围、团队规模、技术项目、论文、模型或产品落地，必须先完整读取并执行 [references/career-model-evidence.md](references/career-model-evidence.md)。以下是不可跳过的完成门槛：

   - 分别建立履历时间线和模型工作表，保留职级、正式职务、管理范围、预算/实际人数、本人角色、技术方法、结果和落地；不得把连续履历压成一个泛化 bullet。
   - 分开记录入职职级与离职前职级；同段中他人的职级不得归给核心人物。采访者推断、本人自述和公开报道必须标明不同证据类型。
   - 严格区分`提出/主导/带队/负责/参与/共同作者/团队完成`；管理某团队不等于亲自发明该团队所有模型，共同作者也不自动等于项目负责人。
   - `100人预算`不得改写成`100人团队`；`在我手里/由我负责`不得弱化成`参与/支持`。预算、在岗人数、协作投入和组织全口径人数分别记录。
   - 技术工作即使另归入“产品与技术”，也必须在人物履历中保留其时间、所属机构和本人角色；技术章节不能替代人物履历的归因。
   - 在输出纪要前完成逐条覆盖检查；任何高重要性职级、组织职责、模型项目、量化贡献或落地结果没有笔记落点时，不得交付。

4. **构建上下文信息库（Context Pool）**
   - 在内存中整理（无需展示，除非用户要求）：
     - **Characters**：人名（正确写法 + 身份）
     - **Terminology**：术语/公司/产品（正确写法）
     - **Corrections**：纠错映射（错误原文 → 正确写法）
     - **EducationClaims**：按人物和学历层级拆分的证据记录（原句 / 材料 / 外部来源 / 状态）
     - **CareerClaims**：按时间拆分的职级、岗位、组织范围和规模证据记录
     - **ModelWorkClaims**：按项目拆分的本人角色、模型/论文、技术、结果和落地证据记录

5. **最终事实投影（Final Fact Projection）**
   - 把`Corrections`、用户更正、公司材料和上下文归一结果一次性应用到最终正文；用户明确给出的别名映射（例如`NovaC`就是`NovaSilicon`）视为当前项目的权威映射，全文统一使用规范名称
   - 最终纪要禁止出现`应为X，并非转写中的Y`、`更可能是X被误写为Y`、`ASR原文为Y`等修改过程；正确结果确认后只写X
   - 对团队人数、产品进度、客户项目、流片、交付和在途融资等早期内部信息，使用简洁来源归因后陈述结果；不要附加“公开检索未找到独立验证”的长段免责声明
   - 对缺失但对本次交流没有直接增量的信息，不生成模板化缺口清单。禁止写`材料未披露出让比例、FA、burn rate和runway，因此无法检验……`之类的通用句；只有当会议明确围绕该问题作出判断时，才保留与结论直接相关的缺口
   - 每个段落应回答“这对理解公司、人物、产品或交易有什么新增信息”。只做关系排除、复述校验过程或罗列未披露字段的段落应删除或改写为有实质内容的事实

### 第二阶段：深度精修（Refinement）

使用第一阶段的信息库，对全文逐段重写。

**精修原则：**

1. **事实修正**：替换所有已核实的错误人名、术语。
2. **语病修正**：
   - 去除口语冗余词（"那个"、"呃"、"然后呢"、"就是说"）。
   - 调整混乱语序，使其符合书面语习惯。
3. **格式保持**：
   - **严禁**合并或删除说话人段落。原文的 `Speaker 1 00:01` 等时间戳标记必须保留。
   - 保持对话交互感，不写成摘要。
4. **推测补全**：对 ASR 乱码或拼音，根据上下文逻辑推断修复。
5. **乱码标记原则（Never Silent Drop）**：
   - 当 ASR 段落包含无法通过搜索确认、也无法从上下文可靠推断的乱码时，**严禁**直接跳过或删除该内容。
   - 在精修稿中保留原文并标注：`[ASR 不清晰，原文："XXX"]`
   - 在笔记稿对应位置插入：`[⚠️ 待确认：原文为"XXX"，疑似指 YYY]`
   - **特别注意**：人名、公司名、产品名的乱码极可能是重要实体——宁可标记存疑也不可丢弃。宁可让笔记"丑"一点，也不能让信息无声消失。

**精修稿输出格式：**
```
# [文件名] 精修稿
**录音日期**：XXXX-XX-XX

---

## 核心修正项
- 修正 "XXX" → "XXX"（经搜索确认）
- ...

---

## 正文

### 00:00:01 Speaker 1
[精修后段落]

### 00:01:23 Speaker 2
[精修后段落]
```

---

### 第三阶段：话题归类重组（Topic Structuring）

基于第二阶段的精修稿，按话题板块重新组织内容。

**内容过滤规则（仅适用于笔记稿）：**

笔记稿的目标是提炼出**被访谈方（创始人/项目方）的有效信息**。以下类型的内容在笔记稿中**应省略**，不归入任何板块：
- **投资人对自身机构的介绍**：如投资人所在基金的背景、LP 构成、投资策略、个人关注领域等（这些是投资人的自我介绍，不是被访谈方的信息）
- **投资人的内部工作流程**：如"我们下周一跟老板讨论"、"我回去跟团队同步"等后续跟进安排
- **本次会议本身的元信息**：包括但不限于——会议如何被安排（谁介绍、何时约的）、参会者阵容（哪几位投资人参会）、会议时长 / 中途打断 / 时间限制、本次访谈双方的关系状态、双方对下一步会面的安排（"拉群"、"下次香港见"、"本轮可能赶不上"等）。这类信息是访谈过程的外壳，不是被访谈方的实质内容。**特别警示**：以下小节标题及任何变体都不应出现在笔记稿中：
  - "[投资机构名] vs [被访谈公司] 的初次接触"
  - "本次访谈的背景 / 缘起 / 安排"
  - "后续动作 / Next Steps"（属于投资人侧的 follow-up）
- **纯寒暄和社交性对话**：如互加微信、告别问候、闲聊天气等

> 判断标准：问自己"如果这个项目以后被另一家不相干的机构看了，这条信息对他们有用吗？"——如果答案是否，就属于会议元信息，不写入笔记。
>
> 注意：这些内容在**精修稿**中仍然完整保留（精修稿不删任何内容），仅在笔记稿中省略。

**参会人信息（必须）：**

笔记稿正文第一行（标题之后、第一个板块之前）必须列出参会人信息，格式为正文文字，不使用任何特殊格式（不加粗、不用列表、不用表格），一行写完。格式示例：`参会人：示例科技创始人王某，投资团队李某、陈某、赵某`。参会人信息从原文中的自我介绍、称呼、说话人标签等处提取；若原文未明确某位参会人的身份/公司，则只写姓名。

**通用归类规则：**

1. **完整段落原则**：每个段落整体归入最匹配的话题，不拆分段落内容。
2. **不丢失原则**：除上述过滤规则明确排除的内容外，所有段落必须出现在某个话题下。若段落横跨多个话题，归入**最主要**的那个，并在段落末尾添加 `[亦涉及: XXX]` 注记。**关键数据指标、人名、公司名、融资金额、收入数字等具体信息必须完整保留，严禁遗漏。**
3. **去除时间戳和说话人**：归类后的段落直接呈现内容，去除所有 `Speaker X 00:00` 标记。
4. **板块内顺序**：同一板块下的段落默认按原始时间顺序排列，**有特殊整理规则的板块（见准备步骤表格）按其规则执行**。
5. **市场与行业**：若文中完全没有相关内容，跳过此板块，不在输出中出现。

**各板块专属整理规则（重要）：**

- **团队背景**：每位核心人员（创始人、CTO 及其他合伙人级关键成员）单独成块呈现：
  - **加粗人名作为标题**，括号内可附中文姓名 / 职位说明，例如：`**Dr. David Zhen Yin（尹振，Founder & CEO）**`
  - 标题下用 bullet point 列表组织该成员的全部信息，**每条 bullet 单独一行**（每条 bullet 的换行由 Markdown 列表语法天然保证）
  - 推荐的内部组织顺序（不强制，根据原文信息密度灵活调整）：
    - **学历**：按"中学 → 本科 → 硕士 → 博士"顺序，写明时间区间、学校、专业；学历段落较长时可作为父 bullet，每段学历作为子 bullet（缩进两个空格）
    - **工作经历**：按时间从早到晚展开；同一时期、同一公司或项目的相关经历合并为一条 bullet，不拆分；做的事情、成就、反思等细节作为该段经历的子 bullet（缩进两个空格）
      - 每段经历须保留原文出现的入职/离职职级、正式岗位、组织范围、预算或实际人数、汇报/决策关系；概括时不得改变数量口径或弱化明确的管理责任
      - **模型与技术工作**：按项目或技术路线列出本人角色、共同作者/团队关系、关键方法、规模、指标及产品落地；不得只列一串技术关键词
    - **当前职务 / 其他角色**（学术任职、政府委员、董事会等）：单独列出
    - **重要荣誉、关键资源、战略意义**：作为独立 bullet
  - 原文中关于该成员的关键信息（履历背景、能力、人脉、判断、过往项目结果、加入时机、负责模块等）必须完整保留，**严禁压缩或省略录音转文字稿中的实质内容**
  - 缺失项不写、不编造（例如出生年份原文未提及就不写）
  - 非核心人员（普通员工、外部合作者等仅被简短提及的人）不单独成块，按需在团队整体信息或正文中简述即可
  - 核心人员的详细信息仍用 **bullet 列表**逐条展开（不用表格替代），因为 bullet 天然支持每条独占一行、层级嵌套
  - **核心成员履历汇总表（必须）**：在团队背景板块的**最末尾**（团队整体信息之后），附一张汇总表，方便快速检索。表格列固定为：`姓名 | 出生年份 | 当前职位 | 学历 | 历史职级/岗位 | 工作经历`。学历列按"中学→本科→硕士→博士"分行（用 `<br>` 换行）；历史职级/岗位按时间列出，并区分本人确认与外部报道；工作经历列按时间从早到晚分行，保留关键组织责任与模型项目。原文未提及的字段填"—"
- **团队整体**：人数、地域分布、组织架构、合伙人持股、招聘策略等团队层面信息单独列为子话题，跟在核心人员之后
- **产品与技术**：识别文中涉及的产品线或子方向，用加粗文字作为标识，相关内容以 bullet point 列出。**注意**：社区/创作者生态的发展路径属于产品板块（因为它是产品驱动的），而非商业化板块。
- **商业化**：收入指标、用户指标、毛利率等核心数据归入此板块；商务合作伙伴关系（如谷歌战略合作）、品牌活动（如 film festival）也归入此板块。
- **市场与行业**：竞品必须**逐一点名**列出，每个竞品单独一条，不可合并为"有几家竞品"。竞争格局分析、模型厂商合作/竞争关系也归入此板块。当原文对多个竞品/同行有**多维度对比信息**（如技术路线、价格、自由度、优劣势等）时，应整理为对比表格，每家公司一行，列头根据原文实际信息灵活设定。
- **融资情况**：
  - **融资进展表（必须）**：只要原文提及融资，无论是已完成、进行中还是计划中，都统一整理为表格。表格列固定为：`状态 | 融资时间/计划交割 | 融资轮次 | 投前估值 | 股东/拟投资方出资情况 | 投后/目标估值`。状态只能使用`已完成`、`进行中`、`计划中`；协议、交割或到账尚未完成的轮次严禁写成已完成
  - 行顺序为：`进行中 → 计划中 → 已完成`；同一状态内按时间从晚到早排列。进行中轮次写明已签约、已发协议、意向或预计出资等实际阶段，不能把目标募集额写成已到账金额
  - 金额和估值优先保留公司交流中的原始币种与单位；只有存在有日期、有来源的可靠汇率时才附换算值。股东/拟投资方出资情况列写明合计融资额及各方金额，未知字段填`—`
  - 资金用途、runway目标和FA信息仅在会议实际提及时放在表格后用bullet列出；未提及就不生成“材料未披露”清单

**结构化笔记输出格式规范（严格遵守）：**

1. 每个话题板块用**四级标题（`####`）**，例如 `#### 团队背景`
2. 板块内需要分类标识的地方（如人名、产品线名、竞品名等）用**加粗文字**，单起一行；这类单独加粗行必须从行首顶格开始，不能作为上一个 bullet 的延续或子项。若加粗行前一行是 bullet、二级 bullet、表格或普通段落，必须在加粗行前插入一个空行；加粗行后若紧接 bullet，也插入一个空行，确保导入飞书时该行成为顶格独立段落。
3. **话题分组规则**：当一个板块内的加粗话题标识**超过5个**时，将相关话题归类到**五级标题（`#####`）**下，五级标题根据话题内容相应命名。例如产品与技术板块有8个产品方向时，可按业务线分组为 `##### To B产品线` 和 `##### To C产品线`，各下辖若干加粗话题标识。话题不超过5个时无需分组，直接用加粗标识即可
4. **表格呈现规则**：当内容天然具有**多维度、多条目的对比/并列结构**时，应整理为 Markdown 表格，而非纯 bullet point。典型场景包括：
   - **融资进展表**：已完成、进行中和计划中的每轮融资各占一行，列为`状态 | 融资时间/计划交割 | 融资轮次 | 投前估值 | 股东/拟投资方出资情况 | 投后/目标估值`（详见融资情况板块专属规则）
   - **竞品/同行对比表**：每家公司一行，列头根据原文信息灵活设定（如公司名、技术路线、价格、优劣势等）
   - **核心成员履历汇总表**：团队背景板块末尾，每位核心成员一行，列为 `姓名 | 出生年份 | 当前职位 | 学历 | 历史职级/岗位 | 工作经历`（详见团队背景板块专属规则）
   - 其他具有天然对比结构的内容（如多方案对比、多产品参数对比等）也优先用表格
   - 表格用于**直观对比和快速检索**，不替代 bullet 列表中的详细叙述——两者互补（先 bullet 详述，后表格汇总）
   - 表格单元格内如需换行，使用 `<br>` 标签（飞书文档的富文本表格支持此语法）
5. 板块内内容用 **bullet point** 展示，**支持二级缩进**：
   - **一级 bullet（`-`）**：主论点、主指标、独立事实
   - **二级 bullet（`  -`，缩进两个空格）**：对上一条的补充说明、细节展开、相关子数据、因果解释
   - 判断标准：如果一条信息**去掉后不影响上一条的完整性**，就应该作为二级缩进；如果它是**独立的新信息点**，就应该作为一级 bullet
6. 板块与板块之间用**分隔线（`---`）**分隔，**分隔线前后不留空行**
7. 章节标题（`####`）与其后内容之间**不留空行**
8. 板块内部各条目之间**不留空行**；例外是规则2中的顶格加粗话题标识，为了避免 Markdown/飞书把它吞进上一条列表，必须用空行明确断开列表
9. **"其他"板块仅在确实存在无法归入任何板块的内容时才出现**；若所有内容都能归入具体板块，则不输出"其他"
10. **中英文间距**：数字/字母与中文字符之间**不加空格**。例如写"7000集""150万美元""TikTok月分成""Claude Code构建"，不写"7000 集""150 万美元""TikTok 月分成""Claude Code 构建"

**笔记稿不含的内容（严禁出现在笔记文件里）：**

笔记稿是**最终消费品**，面向阅读者直接呈现正文内容。以下处理过程中的调试产物一律**不写入笔记文件**：

- ❌ **元数据头**：录音日期、会议地点等（文件名已包含日期；不需要额外的元数据块）。**例外**：参会人信息须在文档最开头以正文格式单独一行列出（见输出格式规范）
- ❌ **核心修正项小节**：ASR纠错映射表是第一阶段的内部调试产物，不写入笔记文件，默认也不在完成消息里展开；仅在用户明确要求查看纠错审计时单独提供
- ❌ **处理过程说明**：任何关于"我做了什么搜索""我纠正了哪些词""笔记省略了哪些内容"的元评论
- ❌ **括号式 ASR 纠错说明**：不要在正文实体后写`（ASR中误作XXX）`、`（ASR原文为XXX）`、`（录音中多次识别为XXX）`这类说明。若正确实体已确认，正文只写正确实体；纠错过程只保留在内部审计信息中。
- ❌ **公开检索缺口代替事实**：公司内部最新进展不因尚未公开而失去信息价值。禁止在正文加入`公开检索未找到能够独立验证……`并罗列合同、验收、sign-off报告等长串取证要求；若信息来自公司，简洁写作`公司表示/会中披露`即可。真正的证据风险放入单独尽调或投资评估，不污染事实纪要
- ❌ **低信息量的未披露字段清单**：禁止为了显得完整而罗列FA、交割时间、现金、burn rate、runway等本次未讨论字段，再得出“无法检验”的空泛结论
- ❌ **人物关系排除清单**：禁止把所有被提及的人名集中成一段并说明“不代表其为成员/客户/顾问/投资人”。保留人物时必须说明此人身份、被提及的具体语境及其对项目判断的增量
- ❌ **ASR 原文溯源注解的过度使用**：一般产品名/公司名/人名纠错后，正文应直接使用正确名（如"明势资本领投"），不必在每处都带"（录音中 ASR 误识为 XXX）"。溯源注解**仅**在以下情况保留：
  - 姓名/机构名仍有多候选未确定（"陈建才 [⚠️ 同名候选：陈健才/陈建军]"）
  - 数字经交叉验证仍不自洽
  - 原文为完全无法识别的乱码（"[⚠️ 待确认，原文为'XXX']"）

以上元数据和调试信息只属于**精修稿**（用户明确要求逐字稿时）或独立的审计记录（用户明确要求时），不属于笔记稿和默认完成消息。

### 第 3.5 阶段：完整性审计（Completeness Audit）

笔记稿初稿完成后，执行以下审计，确保关键信息未遗漏。

**投资访谈模式（模式 A）必查清单：**

| 类别 | 必查项 | 检查方法 |
|------|--------|---------|
| **团队** | 核心人员的**学历（中学/本科/硕士/博士的学校与专业）、职级、正式岗位、组织范围、完整工作经历**——这些是bullet列表必需覆盖的内容；对项目判断有实质增量的人物说明身份与被提及语境；团队总人数及地域分布 | 回到原文逐一核对所有出现过的人名，但只把核心成员或承载重要观点/案例的人写入最终纪要；按第一阶段3h建立学历证据表，按3i建立履历时间线 |
| **产品** | 产品名称（正确拼写）、核心功能、技术架构关键词、合作伙伴 | — |
| **商业化** | ARR/收入、ARPU、用户数（总/月活/付费）、留存率、毛利率、cash flow 状况 | 对每个数字执行交叉验证（见第一阶段步骤 2） |
| **竞品** | 提及的每一个竞品公司名称——**不可写"某竞品"或"未点名"**；如 ASR 未识别出名字，应标记 `[⚠️ 待确认]` 而非省略 | — |
| **融资** | 已完成、进行中、计划中的每轮融资；融资额、估值、出让比例；已提及的机构、FA、时间表、资金用途/runway目标 | 所有轮次都进入融资进展表；融资额÷出让比例≈估值，检查是否自洽；未在会议出现的字段不补缺口清单 |
| **实体反证** | 客户/竞品/合作方/投资机构是否存在工具名污染或近音误识；同一主题下是否出现多个疑似同一实体的名字；人物姓名是否存在二字名/三字名/英文名/昵称未归一 | 执行第一阶段 3f 和 3g：列出本次工具名污染词表和人物归一表，全文搜索近音实体、短名和别名，回看前后 3-5 轮对话；若不能确定则标记 `⚠️` |
| **学历串线** | 每条学校、院系、专业、学位和年份只落在证据明确指向的学历层级；不得把博士信息传播到本科或反向传播；同一句内不得保留与已核实履历冲突的“非正式经历” | 执行第一阶段 3h：逐条回查学历证据表；检查来源是否被错误复用于多个层级，并执行句内冲突检查；确定语气但无合格证据的条目必须删除或改为`⚠️` |
| **职级与组织责任** | 入职/离职职级、正式职务、管理范围、预算、实际团队人数、协作投入和组织总人数口径准确；没有把他人职级归给核心人物，也没有把`负责`弱化成`参与` | 执行第一阶段 3i：逐条回查履历时间线，验证主语、时间、证据类型和数量口径；采访者推断须显式归因 |
| **模型工作与归因** | 核心人物讲述的每个重要模型/论文/技术项目均有笔记落点；本人提出、主导、带队、管理、参与、共同作者和团队完成的归因准确；关键规模、指标和落地未被压成关键词 | 执行第一阶段 3i：逐条回查模型工作表，并在人物履历与技术章节之间做双向覆盖检查 |

**审计动作：**

- 若某必查项在原文中存在但笔记中遗漏 → **立即补充**
- 若原文包含具体案例、运营活动、产品实验或用户共创项目，必须核对并保留其**期数/次数、时间、阶段、负责人、活动机制、参考对象和后续延续情况**；不得只概括成一个抽象标签（如仅写"做过活动"、"做过共创"）
- 若原文给出具体解决方案、增长打法、模型兜底、人工策略或“对投资人/客户/外部不会这么说”的披露边界，必须保留**问题背景、具体步骤、人工/自动化边界、为什么有效、对外叙事与真实做法的差异**；不得只压缩成一个策略名或一句抽象判断
- 若原文是创业、产品或公司战略复盘，必须保留**原始战略假设、人群选择、产品形态拆分、新旧用户是否迁移、组织/技术能力约束、关键决策分歧、后续结果和由此推导出的创业方法论**；不得只写成产品流水账或简单成败结论
- 若某必查项在原文中疑似存在但被ASR乱码 → 先用上下文、用户更正和材料消解；仍无法确认且影响判断时才在笔记中保留一句简短待确认，不展示乱码推断过程
- 若某必查项在原文中确实未提及 → 不补充，不标记
- 若客户/竞品/合作方/投资机构名称与本次工具名污染词表重合，或全文存在同主题近音实体 → 必须完成上下文反证审计，不能只因该实体公开存在就采信
- 若人物出现短名、近音名、英文名、昵称或括号身份说明 → 必须完成人物归一审计，避免把同一人拆成两个名字或沿用 ASR 截断名
- 若核心成员出现任何学历或院系信息 → 必须完成学历证据表和跨层级串线审计；`notes`正文、履历汇总表和后续投资快评中的表述必须完全一致
- 若核心成员出现职级、岗位、团队规模或连续技术项目叙述 → 必须完成履历时间线和模型工作表；人物履历、技术章节、汇总表和后续投资快评中的主语、角色与数字口径必须一致

**高信号段落五表审计（内部执行，不写入笔记）：**

当会议是行业访谈、专家访谈、项目拜访、产品复盘、创业复盘或产品/增长方法讨论时，初稿后必须建立以下内部检查表，再回填笔记：

1. **实体关系表**：`实体 | 角色关系 | 原句主语 | 谓语/判断 | 宾语 | 限定语 | 笔记落点`。用于检查客户、竞品、产品、人物、公司经历是否被错归因，避免把具体产品判断泛化成行业判断。
2. **案例打法表**：`案例/实验 | 背景问题 | 目标人群 | 具体步骤 | 人工/自动化边界 | 结果/信号 | 对外叙事边界 | 方法论`。用于检查运营活动、增长方案、模型兜底、社区共创是否只被压缩成一句抽象结论。
3. **高密度段落覆盖表**：`原文时间段/行号 | 核心信息点 | 是否写入笔记 | 笔记位置 | 省略理由`。连续 2 分钟以上或连续 10 行以上的产品、战略、创业复盘段落，不允许只映射成一个 bullet；若省略，必须属于上文明确过滤项。
4. **核心人物履历时间线**：`人物 | 时间 | 公司/组织 | 入职/离职职级 | 正式岗位 | 管理范围 | 预算/实际人数/协作投入 | 原句与证据类型 | 笔记落点`。用于防止职级、岗位、组织责任和人数口径丢失或串人。
5. **模型工作覆盖表**：`人物 | 时间 | 模型/论文/项目 | 本人角色 | 技术方法 | 参数/数据/算力/指标 | 产品落地 | 合作者/团队 | 来源 | 笔记落点`。用于防止把完成的模型工作压成技术关键词，或把团队成果错误升级为个人发明。

**非投资类会议（模式 B）** 无固定业务必查清单，但仍需回到原文通读一遍，并执行适用的高信号段落五表审计：前三表始终执行；当出现核心人物履历、职级、组织责任或技术作品时，履历时间线和模型工作表也必须执行。确认笔记中不存在整段信息丢失、主语错归因或颗粒度明显不足的情况。

### 第四阶段：材料校验（Material Verification，可选）

**触发条件**：用户额外上传了路演 slides、公司介绍材料、行业研究报告等辅助文件时执行；未上传则跳过此阶段。

**核心原则**：本阶段**仅做事实校验，不改变 notes 的结构和内容完整性**。不增加新板块，不补充新条目，只修正已有内容中事实上的错误。

**执行步骤：**

1. **读取材料**：读取用户上传的辅助文件，提取其中的关键事实信息。

2. **逐项核查**：将材料内容与 notes 稿中的已有表述逐项比对，重点核查：
   - 产品名、模型名是否拼写正确
   - 人名、职位、公司名是否准确
   - 数据指标（融资金额、估值、收入、参数量等）是否与材料一致
   - 时间线、轮次等是否与材料一致

   材料只能核验其**明确写出的字段和层级**。例如 slides 的“博士（北京大学）”只能核验博士院校，不能核验本科院校、院系、专业或年份；材料未写出的字段仍按第一阶段 3h 的证据规则处理。

3. **仅修正错误**：发现不一致时，仅在材料明确覆盖的事实范围内修正 notes 中对应表述；对材料中有但 notes 中未涉及的信息，一律不补充、不新增。材料没有覆盖的字段不得因“同一人物”而被顺带改写。

4. **完成后告知用户**：默认只说明材料校验已应用，不列出逐条修改过程；用户明确要求查看修订记录时再提供摘要。

### 第五阶段：待确认项联网复核（Pending Items Web Verification）

**触发条件**：笔记稿中存在任何 `⚠️` 标记时**自动执行**。这是最终收尾阶段，目标是尽可能消解残留的待确认项。

> ⚠️ **为什么需要单独一个阶段**：第一阶段的搜索是"发现疑似错误 → 搜索验证"，方向是从原文到搜索引擎。但有些 ASR 错误在第一阶段时缺乏足够上下文线索来设计有效查询——只有在完成全文归类、交叉验证数字、比对辅助材料之后，才积累了足够的上下文信息来构建更精准的搜索策略。第五阶段是"带着完整上下文回头再搜一遍"。

**执行步骤：**

1. **扫描残留标记**：在笔记稿中搜索所有 `⚠️` 标记，逐一列出待确认项清单。

2. **分类制定搜索策略**：根据待确认项类型选择搜索方法：

   **公司名/机构名待确认**：
   - 第一轮：按 ASR 原文直接搜索（如"恒力 CRO"）
   - 第二轮：按业务描述反向定位（如"临床前CRO 动物实验 订单翻5倍 2026"）——利用笔记中已整理的业务特征作为搜索线索
   - 第三轮：同音/近音变体穷举（如 hénglì → 恒瑞/恒立/翰力/衡丽），每个变体 + 业务领域搜索
   - 第四轮：利用已知关联实体反查（如"蓝驰创投 种子轮 联合投资方 生物医药"——通过已知投资方反查未知联合投资方）
   - 第五轮：若待确认项是竞品/客户/投资机构列表中的英文短词或疑似音译词，必须执行第一阶段 3e 的升级核验：回原始转写稿定位上下文；普通本地录音若有音频则截取片段重转；播客工作流只回看 PLAUD 文字稿或恢复同一 PLAUD 文件，禁止本地 ASR；再用融资月份、投资方、YC批次、Slack/Teams集成、产品状态等事件线索组合搜索。**不能只用一句"公开搜索未确认"收尾。**

   **海外竞品 / AI产品名称待确认（强制专项）**：
   - 逐个实体建立候选表，至少包含：`ASR原词 | 上下文线索 | 候选公司 | 匹配依据 | 来源链接 | 结论`
   - 优先使用官方或高可信来源：公司官网、YC公司页/Launch、a16z/USV/投资机构公告、Slack/Teams Marketplace、公司官方博客
   - 对听起来像普通单词的名字，不要只搜原词；必须加入业务描述和事件线索。例如：
     - `Victor` + `AI employee Slack Teams` → 可能是 `Viktor`
     - `Pun/Con` + `May a16z AI teammate Slack` → 可能是 `Convey`
     - `ASI/CL` + `YC April agent Slack knowledge work` → 可能是 `Tasklet`
   - 若专项核验后确认真实公司名，笔记正文直接写正确公司名，不保留ASR原词；ASR原词和纠错过程只留在内部审计表。

   **人名待确认**：
   - 按第一阶段 3d 的关系型实体校验方法，但此时可利用更丰富的上下文（如已确认的公司名、已确认的其他人名关系）构建更精准的查询

   **数字不自洽**：
   - 检查对话原文中是否有数字被 ASR 误转（如"一个亿"→"5000万"）
   - 搜索公开融资信息交叉验证（如"[公司名] 种子轮 融资额 估值"）
   - 若仍无法判断哪个数字有误，内部审计表保留完整数学分析；纪要只用一句简洁归因说明两种仍冲突的公司口径

3. **更新笔记稿**：

   - **搜索确认**的项：替换为正确名称/数字，去除 `⚠️` 标记
   - **搜索发现高概率候选**但无法100%确认的项：结合信息重要性处理；不影响项目判断的随口提及直接省略，影响判断的关键实体才保留一句简短待确认
   - **搜索穷尽仍无结果**的项：搜索路径和“未找到”结论只进内部审计表，禁止把`联网搜索未找到匹配的XX`写进纪要
   - **公司内部信息例外**：公司当前进展、客户项目、团队人数和在途融资不要求存在公开网页；只要原始交流与公司材料一致，就按公司口径写入，不产生`⚠️`
   - **核心要求**：对于竞品、客户、投资机构、合作伙伴等关键实体，最终笔记原则上不应残留`⚠️`。完成升级核验仍无法确认时，用最短表述说明冲突本身，不叙述检索过程或证据索取清单

4. **完成后告知用户**：默认只告知纪要已完成核验。只有仍存在会实质影响项目判断的冲突时，才在完成消息中简洁列出待用户确认的结论；不要汇报已经成功纠正的实体、搜索路径或逐条处理表。用户明确要求审计报告时再提供完整复核记录。

## 输出文件

**文件命名规则：**

输出文件名**必须与笔记稿一级标题一致**，格式为 `[YYYYMMDD]-[公司中文名（英文名）]-[行业/主题关键词].md`。不使用源文件名加后缀的方式。

示例：
- 源文件 `20260528-生智数据-腾讯会议转写.txt` → 输出 `20260528-生智数据（BioAZ）-生命科学AI劳动力.md`
- 源文件 `interview-recording.txt` → 输出 `20260115-星辰科技（StarTech）-具身智能.md`

命名要素说明：
- **日期**：从源文件名或内容中提取，格式 YYYYMMDD
- **公司中文名（英文名）**：被访谈方的公司名；英文名用半角圆括号括起；若无英文名则只写中文名
- **行业/主题关键词**：用简洁的词组概括本次访谈的核心主题（如"生命科学AI劳动力""3D生成""AI编程"），不超过10个字

**默认输出（用户未特别说明时）：**

| 文件 | 内容 |
|---|---|
| `[标题].md` | 结构化笔记稿（按话题板块归类，无时间戳） |

**用户明确要求逐字稿时，额外输出：**

| 文件 | 内容 |
|---|---|
| `[标题]-refined.md` | 精修稿（按时间线，保留说话人和时间戳） |
