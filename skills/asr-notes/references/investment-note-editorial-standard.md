# 投资交流纪要编辑规范

项目拜访和创始人交流的纪要必须信息密度高、便于快速阅读，同时保留足以支撑投资判断的来源边界。先在内部完成证据审计，再按本规范投影为最终正文。
## 一、内部来源账本

处理前必须建立`sourceManifest`：上游已提供时直接校验使用；未提供时由本Skill根据用户本轮明确给出的输入生成，默认`notesScope=current_session`、主文字稿为`current_transcript`、其他材料为`verification_only`，不得自行把旧项目文档升级为历史正文来源。每个源只能属于以下一种角色：

| role | 用途 | 是否可贡献正文新事实 |
|---|---|---|
| `current_transcript` | 本次录音／文字稿 | 是；构成本次交流的主体 |
| `historical_record` | 已确认同一实体的历史纪要或项目记录 | 是；仅补耐久事实、履历、技术方法和变化基线，并保留日期 |
| `verification_only` | BP、公司主页、公开网页等核验材料 | 否；默认只纠正／核实当前稿已经涉及的字段，不据此扩写会议纪要 |

`sourceManifest`每项至少记录`path | role | asOfDate | sha256`。`notesScope=current_session`时不得读入`historical_record`；只有上游明确设为`longitudinal`并能唯一证明同一实体时，历史材料才可进入正文。多候选、缺日期或实体归属不唯一时按`verification_only`处理，不得猜选。

随后为每条候选事实记录一个内部来源标签：

`本次录音 | 历史交流（含日期） | 公司材料 | 公开资料 | 用户更正 | 推算`

- 最终正文不展示完整账本、搜索过程或候选排除过程。
- 跨时间引用历史内容时，保留最短必要边界，例如“上一轮交流口径”“在某公司任职期间”。不得让旧材料看起来像本次会中披露或公司当前状态。
- 用户对名称、归属和表述的明确更正优先，但仍需与原始材料核对。用户编辑稿中的推算或新事实不能仅因出现在修改稿里就自动升级为确定事实。
- 公司当前进展可按“公司表示／会中披露”直接写入，不要求公开网页背书；主观判断、用户反馈、行业转述和投资人建议必须保留主语。
- 推算值必须与会中原话区分。出生年份没有直接来源但本科首次入学年份明确时，允许按`入学年份-18`计算，并仅在履历汇总表写`YYYY（推算）`。相邻表格字段即可直接复算的确定性算术只展示结果，公式留在内部账本，不写“据会中金额计算”等过程句；依赖假设、汇率、口径选择或外部参数的估值、稀释和收入推算仍须写`（推算）`并保留最短必要依据。

## 二、保留什么

信息密度指每句话提供具体事实或判断依据，不等于字数更少。不得设置摘要压缩率、总字数目标或每板块固定条数；也不因某个主题占篇幅较多而删掉其证据、例子与限制。先完成原文信息清单与正文落点，再做以下编辑。

优先保留能回答以下问题的信息：

1. 创始人具体做过什么，形成了什么能力？
2. 产品机制如何运作，为什么可能有效？
3. 核心数据是什么，口径和漏斗到哪里？
4. 哪个案例、用户研究或外部反馈改变了产品／商业决策？
5. 当前最重要的验证进展和仍未解决的实质风险是什么？

### 核心人物履历

- 完整执行`founder-profile-format.md`：按`年份—公司／机构—岗位`拆成时间轴，一段经历一条一级bullet，不使用笼统的“工作经历”父bullet。
- 把该阶段最能证明能力的方法、模型、指标、组织责任和产品落地写为二级bullet。不得用“技术背景深厚”“搜索经验丰富”代替模型规模、标签体系、评测阈值、数据处理方法或具体结果。
- 历史交流中的高价值技术细节可以保留，但必须带历史日期或任职阶段；不要与当前公司的技术栈混写。
- 履历汇总表只保留`姓名 | 出生年份 | 当前职位 | 学历 | 工作经历`五列。职级、组织责任和技术项目放在上方详细bullet中，避免表格与正文机械重复。
- 履历汇总表必须由上方已核验的学历／工作经历bullet逐条投影，不重新生成摘要句；每条经历独占一行并以原始、未转义的` <br />`连接，禁止用空格或标点串接多段经历，也禁止把换行 token 放进反引号代码。保存前核对每个单元格的条目数与对应bullet数一致，并在渲染预览中确认页面没有显示字面量`<br />`。

### 产品和决策链

- 对高信号产品机制保留`输入／问题 → 方法／机制 → 输出／效果 → 尚待验证项`，不要只留下抽象策略名。
- 对投资人、客户、专家或历史用户研究的反馈，只有形成产品证据或决策结果时才写入；必须在同一信息单元完整保留`谁组织／参与 → 研究对象与方法 → 得到的具体发现 → 放弃／坚持的产品定位决定`。不得压缩成“深入交流”“给予建议”，也不得因其发生在投资人会谈中而当作关系或融资闲聊删除。
- 关系本身没有信息增量时省略；有决策结果时归入产品、市场或战略，不要误放入融资表，也不要把参与讨论的人写成投资方。
- 创始人对行业为什么长期没做好、自己为什么能做好的反共识判断必须保留。`行业需求存在但旧供给没有做好／缺少能定义行业的人`及标杆公司重塑低效旧行业的类比，不得当作路演闲聊删除；应连同`旧行业问题 → 创始人能力 → 要解决的关键瓶颈`写成完整判断链。概括性类比若由访谈方提出、创始人回应，必须保留真实主语，不得改成创始人直接原话。

## 三、删掉什么

删除以下低信息量内容：

- 搜索路径、纠错过程、候选排除过程和“为什么不敢这样写”的说明；
- 重复出现的“未获独立核验”“不能据此推断”；
- 本次没有讨论的FA、burn rate、runway、交割日等缺口清单；
- 为证明谨慎而堆砌的来源链接、汇率日期和过程性数学推导；
- 对旧成员是否仍在岗、某观点是否已被证明等不影响当前判断的旁支免责声明。
- 只说明“查了什么、没查到什么、为何没有采用某字段”而不增加公司事实或投资判断的整句；删除后不得留下同义改写。
- 无具体证据支撑的“团队经验丰富”“产品具有潜力”“双方进行了深入讨论”“后续仍需关注”等套话，以及已在同一段落说明过的来源备注。若原文给出了具体能力、机制或风险，改写为这些事实；不凭模型常识增加评价或尽调建议。

删除的最小单位是无信息增量的语句，不是含“备注”“未确认”等词的整段。长备注中同时存在收入分母、样本规模、观察时间、计划与实际状态、试点与付费区别时，必须把这些限定并入对应事实。原文未提及的字段直接省略；重要缺口只有在会中实际讨论并影响当时判断时才写。

但不得删除四类必要边界：

1. **归属**：创始人判断、用户反馈、公司口径、投资人建议；
2. **时间**：本次会中、历史交流、公开披露时点；
3. **推算**：估值、稀释、收入等非原话计算；
4. **未解决冲突**：会影响投资判断的实体、数字或材料冲突。

同一小节已明确“会中口径”后，无需在每个bullet机械重复“创始人称／会中称”；但主观判断、第三方反馈、争议或说话人本身影响含义时，必须保留主语。

## 四、结构与视觉重点

- 标题先遵循对话类型，不只概括内容主题。用户已确认是管理层访谈时，文件名与文档标题（`####`）固定为`YYYYMMDD-公司规范名（英文名）-项目方核心受访者短角色 姓名`；联合／共同创始人统一写`联创`，联合创始人兼CTO优先写`联创 姓名`。例如`20260115-示例科技（ExampleTech）-联创 张某`。不得改成“AI模拟芯片设计”等技术主题，也不得把投资机构参会人写进标题。
- 优先使用短句、时间轴、表格和二级bullet；一条bullet只表达一个主结论，细节放到二级bullet。
- 长纪要可选出3—5条最能体现产品差异、核心机制或关键数据的完整句子，用`<u>...</u>`标出，帮助快速扫描。只标正文事实，不标标题、整张表、免责声明或普通背景；不要连续大段下划线。
- 公众号文章、上市公司收入等外部背景数字保留对投资判断有意义的有效位数即可，不照抄无决策价值的过高精度。融资额、估值、转化率、模型指标和会中经营数据仍保留原始有效精度。
- 实体修正必须原子更新：名称、全文出现位置、证据边界和待确认状态一起更新。确认名称后不得继续保留“主体未唯一定位”，也不得让证据栏空白。

## 五、历史纪要整合

当上游提供`priorNotes`、历史交流或现有项目文档时：

1. 仅处理已在`sourceManifest`中声明为`historical_record`的材料；先按本次录音独立生成事实清单，再读取历史材料，避免旧叙事主导本次纪要。
2. 只补入仍有价值的耐久事实、核心履历和技术方法；不要复制整篇旧纪要。
3. 本次材料明确更新旧状态时，以本次为当前口径，并把旧口径用于说明变化。
4. 两期材料冲突时建立内部冲突表；无法唯一消解时保留最短必要冲突，不得把A材料中的行为直接归给B实体。
5. 历史细节进入正文时写明日期或阶段；来源账本必须能够反查到对应文档。

## 六、交付前编辑验收

- 核心人物每段关键经历是否都有时间、机构、岗位和能力证据？
- 连续高信号技术段落是否被压成一个泛化bullet？
- 外部反馈是否保留了证据与决策的因果链？
- 是否仍有可以内部化的审计过程、重复免责声明或未披露清单？
- 每条主观判断是否保留必要主语？跨期资料是否保留时间边界？推算是否标明？
- 名称修正后是否同步清除旧疑点？
- 创始人履历是否遵循独立时间轴bullet、二级能力细节、五列表格和` <br />`换行？出生年份若由入学年份减18得到，是否明确写`（推算）`？
- 是否遗漏了改变产品定位的用户研究／外部反馈，或把反共识行业判断、关键类比压成“深入讨论”？
- 改变产品定位的讨论是否在同一信息单元保留了组织者／参与者、研究方法、具体发现和最终决定，而不是只写“给了建议”？
- 去掉空话后，原文已有的数字口径、失败原因、关键反证、实际做法与对外叙事差异是否仍有真实正文落点？没有用“已概括”掩盖丢失的细节？
- 视觉重点是否少而准，并与Markdown／飞书发布格式兼容？
- 管理层访谈的文件名和文档标题（`####`）是否使用项目方核心受访者的短角色＋姓名，而非模型提炼的讨论主题？

全部通过后，才能把编辑审计标记为`passed`。
