# 数字、实体、别名与上下文反证核验

当输入来自 ASR，或包含数字、人名、公司、机构、产品、术语、疑似乱码／近音词时完整读取。不得把本文件当作可选的低成本检查。

### 第一阶段：上下文分析与实体核实（Context Analysis）

1. **阅读与扫描**
   - 读取用户提供的文本。
   - 识别所有**关键实体**：人名、公司名、产品名、行业术语、缩写。
   - 标记**疑似 ASR 错误**：同音字替换、语义不通、乱码。

2. **关键数字识别与交叉验证（Number Audit）**

   > ⚠️ **ASR 对数字的转录极不可靠**——"2000万"可能变成"2000块"，"5000万"可能变成"50块"。数字恰恰是投资笔记中最不能错的信息，必须专门处理。

   - 扫描全文，提取所有**财务和业务数字**：收入/ARR、融资额、估值、用户数、团队人数、ARPU、留存率、毛利率、runway、月开支等。
   - 对每个数字进行**内部一致性交叉验证**：
     - 例：`ARPU × 月付费用户数 ≈ 月收入 → ×12 ≈ ARR`，检查是否与 ASR 输出的 ARR 数字量级一致
     - 例：`融资额 ÷ 出让比例 ≈ 估值`，检查三者是否自洽
     - 例：团队总人数、各地人数之和是否矛盾
   - 若交叉验证发现数字**不自洽**（差距超过3倍），优先采信由上下文、公司材料或其他数字能够稳定支持的值；推算逻辑只留在内部审计表，纪要直接写结论
   - 公司内部最新进展、团队人数、在手项目和融资推进等信息即使尚未公开，只要说话人和公司材料口径清楚且内部一致，就按`公司表示/会中披露/截至交流时`归因后直接写入；**不得仅因公开网络搜不到就标记为可疑**
   - 只有关键数字在原文、公司材料和内部推算之间仍存在会影响判断的实质冲突时，才保留一句简短标记，如`[⚠️ 数字待确认：公司材料为X，会议口径为Y]`；不要引用乱码ASR原句或展示完整推算过程
   - **严禁**对 ASR 输出的数字不加验证地直接采信

3. **强制联网验证（Mandatory Verification）**
   - 对所有关键实体和疑似错误，**必须联网搜索**验证。
   - 示例：
     - 怀疑"雷君" → Search "小米 雷军"
     - 怀疑"Black Well" → Search "Nvidia Blackwell chip"
   - **禁止猜测**：非 100% 确定的常识都要搜索。

   **3a. 外国品牌名/产品名强制核实规则**

   > ⚠️ **反直觉警告**：**语义合理的英文词作为产品名时危险最高**——Debugging、Triple、Pixel、SWAP、Fire、Vigo 这类词在 AI 圈语境里看起来"像真产品名"，不会触发疑心，但很可能是 ASR 对 Buddy、Tripo、Pexo、Anthropic、Viggle 等真实产品名的误识。**不能因为一个英文词语义合理就跳过核实。**

   遇到以下情况，必须对每一个名字**逐个单独搜索**，而不是扫过去假设它对：

   - **客户列表、竞品列表、投资机构列表、合作伙伴列表**——这类列表中的每个名字都是独立实体，错一个就是一条错误事实
   - **看起来是"普通英文单词"但在上下文里被当作公司名/产品名**的词（如 Triple、Pixel、Debugging、Apple/Amazon 之外的任何英文词）
   - **中文转写的疑似英文发音**（如"龙虾"、"迷失"、"冰江"、"潮信"等在上下文语义里不自然的名词）
   - **英文长词的首尾部分**（如 "SWAP" 可能是 "Anthropic" 前半段辅音的误识；"minus" 可能是 "Manus"；"Solnex" 可能是 "Sonnet"）

   搜索方法：
   - 第一轮：按 ASR 原文搜索，看能否一键找到对应公司官网
   - 若搜不到或搜到的公司与上下文业务领域不匹配 → **高度怀疑是 ASR 误识**
   - 第二轮：按"同发音 + 相同业务领域"搜索替代候选（如"Debugging AI 编程" → Buddy、"3D AI Triple" → Tripo）
   - 第三轮：结合访谈方提及的创始人姓名、融资轮次、客户体量反向定位
   - 第四轮：结合**事件线索**反查，例如"某年某月融资 / 被某基金投资 / YC 批次 / 产品发布 / Slack 或 Teams 集成 / 应用市场上架"。短英文名、普通英文单词、ASR 听起来像单音节的词（如 Pun / Con / Pit）尤其要走这一轮。
   - 仍无法确认 → 进入 3e 的"待确认实体升级核验"，不得直接写成"公开搜索未确认"

   **不接受笔记里存在"听起来是公司名但搜不到"的实体。**

   **3b. 人名处理规则：禁止音译猜测中文名**

   当遇到原文以英文或拼音形式出现的人名时（如 BP 上的 "Dr. Xunfeng Lu"、"Dr. Chuan Tian"），**严禁擅自将拼音音译为具体中文名**：

   - "Xunfeng" 不要写成"迅风"或"训锋"
   - "Chuan" 不要写成"川"或"传"
   - "Liang" 不要写成"亮"、"良"或"梁"
   - "Xiao" 不要写成"肖"或"萧"

   一个拼音对应的中文写法可能有十几种，没有外部权威信息源支持的音译就是**编造**——这种错误的代价比"看起来不够齐整"严重得多（人名错了，访谈对象本人和后续尽调环节都会立刻发现）。

   正确处理方式：
   1. 优先在原始转写稿、BP、提供的其他材料里搜索是否已经给出了中文名（如转写稿里有"我是尹振 David"这样的自我介绍，则"尹振"是可信的）
   2. 联网搜索查证（如 "Xunfeng Lu Stanford Mineral-X 中文名"），如果搜到本人的中文公开资料（领英、公司官网、学术主页、媒体报道）有明确写出中文名，可以使用
   3. 以上都查不到 → **就只用原文给出的英文 / 拼音名，不要附中文名**。例如：`**Dr. Xunfeng Lu（Co-Founder & CTO）**`，括号里只写职位，不强行塞一个中文姓氏或全名

   **底线**：宁可笔记里全是英文名，也不要凭一个拼音就擅自映射出一个中文名。

   **3d. 关系型实体校验（Relational Entity Verification）**

   > ⚠️ **核心洞察**：ASR 转录的人名/公司名即使"看起来像正常中文名"也可能是错的——同音字替换后仍然是合法姓名，但指向了一个不存在的人。**不能因为一个名字"读起来通顺"就跳过校验。**

   **触发条件**（满足任一即必须校验）：
   - 文中出现的**所有人名**，无论是否看起来通顺
   - 文中出现的**所有公司名/机构名**，无论是否看起来合理
   - 特别是在**列举式语境**中出现的名字（"像 XXX、YYY 这些人"、"比如 A 公司、B 公司"）——列举中每个名字都是独立实体，错一个就是一条错误事实

   **校验方法——结合文档上下文设计搜索查询**：

   不要孤立地搜索一个名字（如只搜"蒋行"），而要**利用文档中已知的关系信息构建精准查询**：

   1. **人物关系定位法**：
      - 文中说 A 是 B 的师兄/师弟/同学/前同事 → 搜索"B 的学校/院系/公司 + A 的名字"
      - 文中说 A 在某公司任某职位 → 搜索"公司名 + 职位 + A 的名字"
      - 文中说 A 是某领域知名人物 → 搜索"领域关键词 + A 的名字"
      - 示例：文中说"蒋行是我清华自动化的师兄" → 搜索"蒋行 清华自动化"；搜不到则尝试同音变体"蒋星/姜行/江行 清华自动化"

   2. **公司/机构关系定位法**：
      - 文中说某公司做某业务、在某地、融了某轮 → 搜索"业务领域 + 公司名"
      - 文中说某公司的创始人是谁 → 反向搜索"创始人名 + 业务领域"来验证公司名
      - 搜不到 → 尝试同音/近音变体

   3. **同音变体穷举**：
      - 对于搜索不到的中文人名，列出所有可能的同音字组合逐一尝试
      - 对于搜索不到的英文名，考虑 ASR 可能的音素级错误（如 Fellow → Pharaoh / Pheno / Hallow）
      - 每个变体都要结合上下文信息（行业、关系、地域）搜索验证

   4. **校验结果处理**：
      - 搜索确认存在且背景吻合 → 直接使用正确名
      - 搜索找到同音替代且背景更吻合 → 在内部纠错映射中记录，笔记直接使用正确名，不展示替换过程
      - 所有变体均搜索不到 → 先判断信息重要性；影响团队、客户、产品、融资或投资判断的实体才保留一句简短待确认，低信息量、与项目无直接关系的随口提及不进入最终纪要
      - **严禁**对搜索不到的名字不做任何标记就直接采信

   **底线**：笔记中出现的每一个人名和公司名，要么经过搜索验证确认，要么有清晰的公司/会议归因；不要把一串被提及的人名集中列出并解释“他们不属于公司”。只有具备信息增量的人物才进入纪要，并写清楚`此人是谁 + 在什么语境被提到 + 该提及说明了什么`。例如，行业专家被用来说明技术路线变化时，应写其研究方向和该案例如何支撑项目判断，而不是只写名字或关系排除声明。

   **3e. 待确认实体升级核验（Escalation for Unresolved Entities）**

   当某个实体满足以下任一条件时，不能只做普通搜索后标"待确认"，必须升级处理：

   - 出现在**竞品、客户、投资机构、合作伙伴**列表中
   - ASR 输出为很短的英文词、普通英文单词或疑似音译词（如 Victor / Pun / Con / CL / ASI）
   - 原文同时给出融资时间、投资机构、YC 批次、产品形态、Slack / Teams / Discord / Telegram 等关系线索
   - 初次搜索找不到，但该实体对投资判断或竞争格局有实质影响

   升级处理必须依次执行：

   1. **回到原始转写稿**：定位该实体前后至少 3-5 轮对话，提取所有关系线索（业务描述、投资方、月份、轮次、集成平台、产品状态）。
   2. **若有音频文件且不是播客工作流**：截取该实体前后约 60-90 秒音频，用本地 ASR 重转一次；`--context` 中加入候选公司名、投资机构、业务关键词和平台名（如 `Viktor Convey Tasklet a16z USV YC Slack Teams AI employee AI teammate`）。`sourceKind=podcast` 时禁止本地重转，只回看 PLAUD 文字稿或由上游恢复同一 PLAUD 文件。
   3. **组合搜索查询**：至少覆盖三类查询：
      - ASR 原词 + 业务领域（如 `"Pun" "AI employee" Slack`）
      - 事件线索 + 业务领域（如 `"May" "a16z" "AI teammate" Slack`、`"YC" "April" "agent" "Slack"`）
      - 候选名称 + 官方/权威来源（官网、YC、a16z / USV / 投资机构公告、Slack / Teams Marketplace、公司博客）
   4. **交叉确认**：只有当候选公司同时匹配发音/误识可能性、业务描述和至少一个关系线索时，才能替换进笔记。若只能确认其中一部分，在笔记里保留 `⚠️` 并写清楚"已查到的候选是什么、哪些线索匹配、哪里仍不确定"。

   **禁止行为**：
   - 禁止把 `Victor/Pun（名称需核对）` 这类未解析字符串直接留在最终笔记里，除非已完成上述升级处理。
   - 禁止只写"公开搜索未确认"作为结论；这通常说明搜索查询设计不足，而不是实体真的不可确认。
   - 禁止把描述性缩写当作公司名采信。例如 `ASI` 可能只是"Artificial Superintelligence"类描述或 ASR 误识，必须结合 YC / 融资 / 产品线索反查真实公司名。

   **3f. 工具名污染与上下文反证审计（Tool-Name Contamination & Context Countercheck）**

   > ⚠️ **真实存在的错误实体最危险**：ASR 可能把一个近音客户/竞品误识成处理流程中刚使用过的工具名，或误识成另一个真实存在的公司名。不能只问"这个名字是否存在"，还必须问"这个名字在这段对话里是否应该存在"。

   **触发条件**（满足任一即必须执行）：
   - 本次处理链路用到的工具、平台、模型或服务名（如 `Plaud`、`Claude`、`Qwen`、`Codex`、`飞书`、`Whisper` 等）在转写稿中又被当作**客户、竞品、投资机构、合作伙伴、被访谈公司或产品**出现
   - 原文出现`X 是我客户`、`X 是竞品`、`X 在融钱`、`X 投了谁`、`X 是合作方`、`我们在给 X 做`等关系型句式
   - 同一主题在全文不同位置出现近音或同领域实体（如 `Plaud / Slock / Slack / Raft`，`Krea / Kira`，`Vmake / VidMuse / V6 / Buzz`，`Loopit / Locket`，`Coda / Canva`，`web coding / vibe coding`，`Cloud / Claude / Code`，`Lib / Live / Luma`）
   - 实体虽然公开存在，但与该段业务语境不完全匹配，或只在单个 ASR 片段中出现、缺少后续语义支撑

   **审计动作**：
   1. **建立本次工具名污染词表**：把本次转写、整理、写入过程中使用过的工具/平台/模型名列入高风险词表。词表中的名字若出现在客户/竞品/合作方语境，不能直接采信。
   2. **回看上下文**：定位该实体前后至少 3-5 轮对话，提取业务描述、产品形态、客户类型、集成平台、上下游关系、融资或商业化线索。
   3. **全文反证扫描**：搜索全文是否有同一话题下的近音实体、别名、后续解释或反向证据。若后文持续讨论另一个实体且业务语义更吻合，优先怀疑前文 ASR 误识。
   4. **候选表判断**：对关键实体建立候选表，至少包含：`ASR原词 | 时间戳 | 上下文业务 | 候选实体 | 支持证据 | 反证 | 处理结论`。
   5. **必要时重听/重转**：若有音频文件、实体影响判断且不是播客工作流，截取该实体前后 60-90 秒音频重转；`--context` 中加入候选实体和业务关键词。播客只允许回看 PLAUD 文字稿或恢复同一 PLAUD 生成，不使用本地 ASR。
   6. **关系主谓宾保真**：对`X 是客户/竞品/合作方`、`X 要超越 Y`、`X 来自/做过/投了 Y`、`我们给 X 做`等关系型句式，抽取`主语 | 关系 | 宾语 | 限定语 | 上下文`，再写入笔记。改写时不得把具体主语泛化、置换或挪给同领域实体，例如不得把`Loopit 很难超越 TikTok`写成`泛娱乐产品很难超越 TikTok`，也不得因工具名污染把`Slock 是客户`写成`Plaud 是客户`。

   **处理规则**：
   - 若上下文和后文反证显示ASR原词不匹配，直接改为更吻合的候选，修正逻辑只进内部审计表。
   - 若只能判断ASR原词可疑但无法确定候选，仅在该实体影响项目判断时简洁标记：`[⚠️ 实体待确认：疑似指Y，现有上下文不足以唯一确认]`；不展示原始误写和推理链。
   - 若实体来自工具名污染词表但最终确认确实为该实体，只在内部审计表记录“已排除工具名污染”；最终纪要直接使用正确实体。
   - 禁止因为某个名字是公开存在的真实产品/公司，就跳过上下文一致性检查。

   **3g. 中文姓名截断与别名归一（Chinese Name Alias Canonicalization）**

   > ⚠️ **二字人名也可能是三字姓名的截断**：ASR 常把中文三字姓名漏掉第一个字，或把英文名/昵称/职务线索拆成另一个"看起来正常"的人名。人名处理不能只校验"这个二字名是否像中文名"，还要判断它是否与全文里的同一身份指向一致。

   **触发条件**（满足任一即必须执行）：
   - 同一人物在全文中同时出现二字名、三字名、英文名、昵称或括号身份说明（如`Albert那边的产品经理`、`之前在某公司同事`）
   - 二字人名出现在"有没有跟你说过"、"我和X在某公司/某项目组"、"X那边的人"、"X要出来创业"等关系型语境中
   - 用户、标题、辅助材料或已有知识库提供了更完整姓名，但 ASR 正文出现了更短或近音写法
   - 同一段履历、职位、项目经历只能合理对应一个人，但笔记中出现两个相近人名

   **审计动作**：
   1. **建立人物归一表**：记录`ASR人名 | 可能全名/英文名/昵称 | 身份线索 | 出现时间戳 | 处理结论`。
   2. **按身份而非字面归并**：优先使用公司、项目组、职位、共同经历、英文名、介绍人等关系线索判断是否同一人；不要因为二字名表面成立就当作另一个人。
   3. **全文扫描短名**：当确认`程兆华`这类全名后，继续搜索`兆华/赵华/朝华/昭华`等短名或同音变体，统一替换或标注。
   4. **用户更正优先**：用户明确指出"文档里的X是指Y"时，以用户更正作为当前文档的权威映射，立即更新结构化笔记和外部文档；原始转写稿可保留 ASR 原文作为溯源。

   **处理规则**：
   - 若身份线索明确指向同一人，笔记中统一使用完整、可识别的姓名；必要时首次出现可保留括号身份说明。
   - 若只能确认二字名疑似为某三字姓名但证据不足，仅在该人物具有实质信息时写作`[⚠️ 人名待确认：疑似指Y]`；依据和原始误写保留在内部人物归一表。
   - 禁止把同一身份拆成两个不同人写入笔记；也禁止在用户已给出明确更正后继续沿用 ASR 误识名。
